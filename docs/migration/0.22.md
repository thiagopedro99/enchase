# Migrating to 0.22

From 0.21.x. This page only quotes the notes of the release, and the whole of them are in the [changelog](../../CHANGELOG.md#v0220).

## Does it break?

> No breaking change at run time, and the stable API did not lose anything: `npm run check:api` against 0.21.1 reports 22 keys of `exports` (one more, `./css/*`) and none removed, 12 stable entries with 1,120 lines of declarations (2 more than the 1,118 of 0.21.1: `value` of `BreadcrumbItem` and `contrastChecks` of `enchase/theme`) and none removed or changed, one widened (`BreadcrumbItem.id`, from required to optional), the same 1,223 `--enchase-*` names and 279 `data-slot` names, and the same 578 hooks of the styles.

> One change can show in your compiler, and it is the one to check: `id` of `BreadcrumbItem` is optional now, so passing items works as before, and only code that reads `.id` from an item that it typed as `BreadcrumbItem` sees `string | undefined`.

## If you pass items to the `Breadcrumbs` or to the `Layout`

> `BreadcrumbItem` takes `value` as the name of an item, as `TabsItem`, `AccordionItem` and `SegmentedControlItem` do, and keeps `id` until 1.0.

> The type stays one flat shape, with `value?: string | undefined` and `id?: string | undefined`, and an item with neither is valid.

> The React key of an item is its `value`, else its `id`, else its position in the whole trail, not in the collapsed list, so the node of an item without a name is kept when the ellipsis opens the trail.

> `value` wins over `id` when both are given, and neither is written to the DOM: the markup, `aria-current` and the `data-slot` names are the ones of 0.21.1.

> `id` is documented as the name that stays until 1.0 in `API.md`, in the README, in `skill.md` and in a new section of `VERSIONING.md`, "Names kept until 1.0", and the editor does not flag it.

## If you ejected the `Breadcrumbs` or the `Layout`

> The kit of `enchase eject` has the same 304 files, and 3 of them have new content, the copies of the `Breadcrumbs`, of its types and of the trail of the `Layout`, which `enchase eject --diff` shows to whoever ejected them before.

## If you want less css

> `enchase/css/<name>.css` is the css of one component, cut from `styles.css`: 47 files, one for each component that has css (`button.css`, `button-link.css`, `date-picker.css`, `layout.css`), and `enchase/css/index.json`, their map, both behind the new export `./css/*`.

> The map is `{ format: 1, components }`, and each component has its `file`; its `needs`, the components whose css comes before it, in the order to import them (`button-link` needs `icon`, `button` and `visually-hidden`), which is the closure of what the javascript of the component reaches; its `files`, the css modules of the sources that make the file, in the order that they have in `styles.css`; and its `bytes` and `gzip`.

> The names of the files, the format of `index.json` (`format: 1`, with `file`, `needs`, `files`, `bytes` and `gzip`) and the equivalence with `styles.css` are public API from the start, in `VERSIONING.md`: a new file or field is a minor version, and renaming or removing a file, changing what a field means or the format, or taking a rule out of a file is a break.

## If you use `contrastChecks`

> `enchase/theme` exports `contrastChecks(colors)` again: it was one of the 37 internal helpers that left the entry in 0.10, and it returns as part of the contract, with `ContrastCheck`, which was already exported as a type.

> A color token that is added brings its pairs, so the list can grow in a minor version, and the documents say so.

## If you test with screen readers

> Screen readers: nothing changed in what the components render.
