### Notes

- No breaking change. New: `Combobox` and `DatePicker`; the `Checkbox` takes `indeterminate`; the `Table` selects rows; the locales have eight new optional labels, and `enchase/icons` a new icon (`CalendarIcon`, 20 in all). Fixed: when a `Popover` opens by keyboard, it no longer moves the focus away from something its content has already focused.
- `Checkbox` takes `indeterminate` (a boolean, `false` by default) for the mixed state of a box that sums up others, such as a "select all". HTML has no attribute for it, so the component sets the `indeterminate` property of the native `<input>`, and the screen reader reads "mixed" from the native mapping. `checked` is never touched: a box can be checked and mixed at once, and the value in a form is still the one of `checked`. The browser clears `indeterminate` on a click, so the component puts the value of the prop back right after the click, once React has handled `onChange`: the prop rules, a click never clears it alone, and the app clears it in its `onChange`, as the usual "select all" does. The look comes from `:indeterminate`, the same source the screen reader reads, so a box rendered on the server shows as checked or unchecked until the page hydrates (the server cannot render the mixed state). It is drawn as the checked box is (the same fill and border hooks, and the `-checked-disabled` ones when disabled) with a dash where the tick goes, sized by `--enchase-checkbox-box-size` and `--enchase-checkbox-box-check-width`: no new hook. A mixed invalid box does not get the error border, as a checked one does not, and in forced colors the dash stays visible.
- `Table` selects rows. Pass `selectedKeys` (a list of keys, even an empty one, turns the column on) and `onSelectedKeysChange`; there is no state of its own, as with `sort`. The key of a row is the one `getRowKey` gives, or its index: with sorting, pass `getRowKey`, or the selection follows the position and not the record. The first column is a `th scope="col"` with the "select all" `Checkbox` (checked when every row is selected, `indeterminate` when some are, disabled with no rows and while loading) and a `td` with a box per row; a selected row gets `data-selected` and never `aria-selected`, because this is a table and not a grid. "Select all" adds the rows that are missing (no repeated keys, the order of what was already selected is kept) and, with every row selected, takes out only the keys of the rows of the table, so a selection that spans several pages keeps what is on the other pages; keys that belong to no row are ignored in the count and kept in what is reported; `1` and `"1"` are different keys. Every box has a name: "Select row" joined with the cell of the first column marked `rowHeader` (so a reader hears which row), and "Select all rows". Two new optional labels carry the texts (`selectRow` and `selectAllRows`). The look: a narrow first column with no vertical padding (the box already has the hit size), a selected row filled with `--enchase-table-row-background-selected` (the container-high surface by default, one new hook), the hover layer over it, and the same width of the column loading and loaded. Out of scope: single selection, selection by range with Shift, disabled rows and a selection the table keeps by itself.
- `Combobox` is a text field with a list of options under it, in the ARIA 1.2 pattern: the focus never leaves the input (`role="combobox"`, `aria-expanded`, `aria-controls`, `aria-autocomplete="list"` and `aria-activedescendant`), and the list is a `role="listbox"` in a portal, named by the label. Typing filters, the arrow keys move through the list and skip the disabled options (and wrap), Home and End go to the ends, Enter chooses the active option, Esc closes (keeping the text) and Tab leaves; ArrowDown opens on the first option, or on the chosen one, ArrowUp on the last, Alt+ArrowDown opens and Alt+ArrowUp closes. Props: `options` (`{ value, label, disabled? }`), `multiple`, `value`, `defaultValue` and `onValueChange` (`string | null` by default, `string[]` with `multiple`: the type is a union discriminated by `multiple`), `label`, `labelPlacement`, `error`, `helperText`, `placeholder`, `fullWidth`, `filter`, `onInputChange`, `loading`, `open`, `defaultOpen`, `onOpenChange`, `name`, `form`, `container`, `animation`, `id`, `wrapperClassName`, `wrapperStyle`, `listboxClassName`, `listboxStyle`, and the attributes of the `<input>`; `ref` goes to the input. The default filter keeps the options whose label contains the text, ignoring case and accents; pass a function `(option, query) => boolean`, or `false` to show every option, for a search on a server (`onInputChange` and `loading` tell the app what was typed and show a row that says so, with `aria-busy` on the list and a status region). The value is always the `value` of an option, never the text typed: when the user leaves the field, the text goes back to the label of what is chosen, and emptying the text and leaving clears the choice (`onValueChange(null)`); choosing again the option that is already chosen does not call `onValueChange`, as a native `<select>` does. With `multiple`, the list stays open after a choice, the text is cleared, every choice becomes a `Tag` with a button that removes it (its name is "Remove" plus the label) and Backspace in an empty field removes the last one. The label of a chosen option is remembered, so an app that replaces `options` while the user searches does not empty the field or the tags. `name` (and `form`) render a hidden `<input>` per chosen value, and the visible input has no name. A disabled or read-only field does not open. Two new optional labels carry the texts: `noResults` and `showOptions` (the button), and the loading text is the `loading` label that already existed.
- The list of the `Combobox` is not a `Popover`: the `Popover` moves the focus inside and has the semantics of a dialog, which takes the focus away from the field. It is a `ListboxPopup` of its own, with the same hooks the `Popover` uses (presence, the overlay stack, the tree of popovers, the portal container, the positioning), so it opens under the field at least as wide as it, turns up when there is no room, closes with Esc (only the front layer: an Esc inside a `Modal` closes the list first and the `Modal` on the next one), with a click outside and when the focus leaves the field, and renders in a portal on `<body>`, or in `container`. The mouse down on the list is cancelled, so the focus stays in the field. The active option follows the pointer through `pointermove`: a finger does not activate anything (it left an option marked after a touch, found in Chromium with touch emulation), and a trusted move with the same coordinates as the one before is dropped (found in WebKit: it fires a `pointermove` when the list scrolls under a still mouse, and the active option went back to the one under the pointer while the arrow keys walked).
- `DatePicker` is a field for a single date. The user types it, in the order and with the separators of the language of the `UIProvider` (28/10/2026 in pt-BR, 10/28/2026 in en; the compact 28102026 and the ISO 2026-10-28 are read too) or presses the button at the end of the field to choose it in a calendar that opens in a dialog. The value is a string in the local ISO form, `YYYY-MM-DD`, with no time and no time zone (the text `<input type="date">` gives), or `null` for an empty field: no `Date` object is involved in the arithmetic, so the day never moves with the zone of the machine (the tests run in four zones, from UTC-11 to UTC+14). Props: `value`, `defaultValue` and `onValueChange`, `min`, `max`, `isDateDisabled` (it receives each date as ISO and returns `true` for the ones that cannot be chosen), `firstDayOfWeek` (0 to 6, the language of the provider by default), `label`, `labelPlacement`, `error`, `helperText`, `placeholder`, `fullWidth`, `open`, `defaultOpen`, `onOpenChange`, `name` (a hidden input holds the ISO text), `form`, `container`, `animation`, `id`, `wrapperClassName`, `wrapperStyle`, `popupClassName`, `popupStyle`, and the attributes of the `<input>`; `ref` goes to the input. The text is a draft, as in the `NumberInput`: it is read when the user leaves the field or presses Enter (which also closes the calendar), and a text that is not a date, or that `min`, `max` or `isDateDisabled` rule out, is put back as it was without calling `onValueChange`, while an empty text clears the date. The calendar is the `Popover` of the library with `role="dialog"` named by a label, anchored to the whole field and not only to the button; when neither side of the field has room for all of it, it opens on the side with more room and its body scrolls. It opens with the focus on the chosen day, or on today, by a click and by the keyboard (an open calendar that is there from the first render does not take the focus), and Esc and the choice of a day close it and give the focus back to the button. Today is read in the browser when the calendar opens, so the server renders only the field. The calendar stays internal (nothing about it is exported): it is a `role="grid"` table named by the month, with the arrow keys by a day and by a week (swapped in right-to-left pages), Home and End for the start and the end of the week, Page Up and Page Down for the month and Shift with them for the year, Enter and Space to choose, `aria-selected`, `aria-current="date"` for today, `aria-disabled` for the days that cannot be chosen (they stay in the grid and can be reached, as the grid pattern asks), the title of the month in a polite live region, six weeks always (so the height does not jump), the days of the neighbor months selectable, and buttons for the previous and the next month that stop when the whole neighbor month is out of range. The names of the months and the weekdays, the first day of the week and the mirroring follow the language of the provider; the field has the look of the `Input` (every `--enchase-input-*` hook applies) and its own hooks (`--enchase-date-picker-*`: the corners, the messages, the button and the whole calendar, 33 in all, listed in `API.md`). Four new optional labels carry the texts: `openCalendar`, `chooseDate`, `previousMonth` and `nextMonth`. Out of scope: ranges of dates, time, several dates and a list to pick the month or the year.
- Internal, not exported: the date utilities (`calendarDate`, `firstDayOfWeek`, `dateFormat`), written in integers with the Gregorian calendar (`Intl.DateTimeFormat` with `calendar: 'gregory'` and `timeZone: 'UTC'`, the order and the separators of each language from `formatToParts`, the digits of 19 numbering systems and years below 1000 written with four digits). The first day of the week comes from `Intl.Locale#getWeekInfo()` (or the older `weekInfo` property) and, where the platform gives neither, from a table by region that a browser test compares with the `Intl` of each engine for every region it knows (more than 200): only `AE` and `IS` differ, and they differ between the engines themselves.
- `Popover`: when it opens by keyboard it moves the focus to the first focusable element of its content, and it did that after the content had already put the focus where it wanted (a child's `autoFocus`, or an effect), so the content lost. It now leaves the focus alone when it is already inside the content. Nothing changes for content that does not move the focus: the first focusable element, the body or the content itself are still the destination. (The `DatePicker` needs it to open on the chosen day.)
- Eight optional labels in `UILabels`, in the `en` and `pt-BR` locales and in the test of the locales, with the English text as a fallback for a custom locale that does not have them: `selectRow`, `selectAllRows`, `noResults`, `showOptions`, `previousMonth`, `nextMonth`, `openCalendar` and `chooseDate`. The sentence of `README.pt-BR.md` that lists the optional keys of a custom `locale` was out of date since 0.10.0 (`removeTag`) and is complete again. Together they weigh about 340 bytes minified in the `en` locale that every component that reads the configuration carries.
- `enchase/icons` has a new icon, `CalendarIcon`, 20 in all, because the `DatePicker` uses it (the test that keeps the list equal to what the components import caught it).
- The shadcn style tunes the new components: `combobox` and `date-picker` joined the list of fields (helper and error in `sm`), the options and messages of the `Combobox` have the padding, corners and `sm` text of the ones of the `Select` and the `Menu` of the style, and the calendar of the `DatePicker` has its title and its days in `sm` and its weekdays in `xs`.
- Screen readers: the speech of the new patterns was not heard with a screen reader (the README says it of the whole library: nothing was tested with NVDA, JAWS or VoiceOver). The roles, the names, the states and the focus are tested in Chromium, Firefox and WebKit. Where readers tend to differ, and what to listen to first: how the `Combobox` announces its active option while the focus stays in the input, and its "No results" and "Loading" messages (a disabled `role="option"` in the list and also a `role="status"` region, so a reader may count them in the list or say them twice), what the `DatePicker` field says about its format (nothing, unless you pass `placeholder` or `helperText`), how a day of the calendar is read (the weekday, the month, the day and the year, with `aria-selected`, `aria-current="date"` and `aria-disabled`) and the month title that is announced when it changes, and the mixed state of the `Checkbox` with the names of the row boxes of the `Table`.
- Docs: the Storybook has 33 new stories (sixteen for the `Combobox`, fourteen for the `DatePicker`, an `Indeterminate` and a `SelectAll` for the `Checkbox` and a `Selectable` for the `Table`), 313 in all against the 280 of 0.11.0. `API.md` and the READMEs list the new components, `README.pt-BR.md` has their rows and props, and `skill.md` records the contract of each.
- With the default style the look of the components that already existed is the one of 0.11.0. A computed-style audit of the 280 stories of 0.11.0 (the 33 new ones left out), in Chromium, Firefox and WebKit, in the light and dark modes and in the base, tab, hover and pressed states, compared about 85,400 values per browser against the Storybook of 0.11.0 and found no difference of value in any component that existed: the only CSS of a component that existed that changed is the one of the `Checkbox` (the mixed state) and of the `Table` (the selection column), neither of which any of those stories uses. What the comparison lists comes from the capture and not from the library: the gallery of the `Icon`, which has a new icon (`CalendarIcon`) that moves the others (82 nodes that appear or disappear at another position), the options of a native `select` in the pressed state (3 stories, in both directions) and, in WebKit, the color inherited by an element under an ancestor with `display: none` (`components-select--label-above`, dark mode: WebKit does not recalculate the style of what is not drawn).
- Weight: with the default style, `enchase/styles.css` goes from 21.1 to 23.6 kB gzip (181.3 to 213.6 kB raw), with the CSS of the `Combobox`, the `DatePicker` and its calendar, the selection of the `Table` and the mixed state of the `Checkbox`; `enchase/theme.css` does not change. In JavaScript (gzip, minified, React external), every component that reads the UI configuration gets about 0.1 kB heavier, the cost of the eight new messages of the `en` locale that it carries (`Button` 2.86 to 2.96 kB, `Modal` 6.32 to 6.42, `Popover` 8.64 to 8.75, `Layout` 17.17 to 17.28); the `Checkbox` goes from 3.38 to 3.68 kB (the mixed state), the `CheckboxGroup` from 3.95 to 4.25, the `Table` from 4.39 to 5.86 (the selection, with the `Checkbox` inside) and the shadcn style from 7.07 to 7.16. The `Select`, `Textarea`, `Divider`, `Avatar`, `Icon`, `ColorModeProvider` and `createTheme` do not move. The new ones weigh only for whoever imports them: `Combobox` 11.59 kB (it carries the `Tag`, the list navigation, the positioning and the icons) and `DatePicker` 14.33 kB (it carries the `Popover`, the calendar and the date utilities).

### Notes

- No breaking change. New: `Drawer`, `Menu`, `Slider`, `SegmentedControl` and `CheckboxGroup`; the `Table` sorts (the app orders the rows, the table draws the buttons and marks `aria-sort`), can keep its header in view, shows a loading state and takes nodes as headers; and the `Popover` takes `role="menu"`. Fixed: the arrow of the `Popover` was never visible, and a long word in the label of a `Checkbox` pushed its container wide. One thing to check if you style the `Popover` yourself: its content box does not scroll any more, a new `popover-body` inside it does (details below).
- `Popover` arrow: with `arrow` on, the content box had `overflow: auto`, which clipped the half of the arrow that sits outside the box, and the half inside had the color of the background, so the arrow could not be seen (it sat 7 px above the content, measured in Chromium, Firefox and WebKit). The content box carries the background, the border, the shadow and the arrow now and no longer scrolls; the new `data-slot="popover-body"` inside it scrolls and carries the padding. `--enchase-popover-content-padding-*` still work (they apply to the body), the default look is the same, and CSS of yours that sets `padding` or `overflow` on `[data-slot="popover-content"]` has to aim at `popover-body`. The border (`--enchase-popover-content-border-width`, `0px` by default) is drawn on the two outer sides of the arrow too. When the content has nothing to focus, the focus goes to the body (`tabindex="-1"`).
- `Popover` takes `role="menu"` besides `dialog`, `listbox`, `tree` and `grid`. With `menu`, Tab and Shift+Tab close it (Tab goes on to the element after the trigger, Shift+Tab returns to the trigger) and the scrolling body has no `tabindex`, because the items hold the focus. The other roles are as they were. `usePopoverControl`, internal and not exported, gives the content a `close()` and its `contentRef`.
- `Menu` is a button that opens a list of actions: a `Popover` with `role="menu"`. Its props are `items` (an item is `{ id, label, textValue?, icon?, disabled?, onSelect? }` and a divider is `{ id, separator: true }`), `label` (required: the name of the list, never shown), `open`, `defaultOpen`, `onOpenChange`, `placement` (`bottom-start` by default), `offset` (4), `container`, `animation`, `className` and `style` (the wrapper of the button), `contentClassName` and `contentStyle` (the box) and `children`, the trigger, which is cloned. The trigger gets `aria-haspopup="menu"`, `aria-expanded` and `aria-controls`; ArrowDown opens on the first item, ArrowUp on the last, and a click, Enter or Space open with the focus on the first. Inside, the arrow keys move (and wrap), Home and End go to the ends, typing a letter goes to the next item that starts with it (it uses `textValue`, or the label when that is text), and only one item is in the tab order. A disabled item is `aria-disabled` (never `disabled`), is skipped by the keys, does nothing and keeps the menu open. Enter, Space or a click on an item runs `onSelect`, closes and returns the focus to the trigger; Esc closes and returns the focus; a click outside closes without taking the focus from where it landed. `defaultOpen` does not steal the focus. Out of scope, on purpose: submenus, checkbox and radio items and items with `href`. Hooks `--enchase-menu-*`.
- `Drawer` is a panel that slides in from one edge of the page, in a portal on the `body` (or in `container`, resolved after mount, never on the server), with the focus trapped, the rest of the page `inert`, the scroll locked, Esc (only the front layer closes), a click on the overlay (it ignores a click that started on a layer above, as the `Modal` does) and an animated exit. Props: `open` and `onClose` (always controlled), `title` (an `h2` that names it) or `ariaLabel`, `children`, `footer`, `side` (`start`, the default, or `end`, which mirrors in right-to-left pages), `size` (`sm` 320, `md` 400, `lg` 560 px, never more than 90% of the screen), `showCloseButton`, `closeOnOverlayClick`, `closeOnEsc` (all `true`), `container`, `animation`, `className` and `style`. The close button uses the `closeModal` label that already existed. The panel travels its own width, and `animation.tuning.distance` only counts when it is larger than the panel; with reduced motion it does not slide. Hooks `--enchase-drawer-*`, in the same design as the `Modal`'s, and the border of the panel is only on the inner edge. The library reserves `scrollbar-gutter: stable` on `html`, so the fixed area is narrower than the window by the width of the scrollbar, and a `Drawer` on the `end` side stops there, as the drawer of the `Navbar` already did.
- The drawer of the `Sidebar` (in its modal mode) and the one of the `Navbar` run on the same internal layer as the `Drawer` now (the root, the overlay and the panel, with the overlay stack, the modal behavior, `role="dialog"` and `aria-modal`). Their DOM is the one of 0.10.0 in the 14 states measured (open, entering, leaving and closed, left to right and right to left), and their CSS and hooks did not change. One alignment: a click on the overlay of both now ignores a click that started on a layer above, as the `Modal` always did; it makes no difference with a single layer.
- `CheckboxGroup` is the sibling of the `RadioGroup` for several choices: a `<fieldset>` with a `<legend>` (`label`), `error` (with `role="alert"`, replaces the `helperText`) and `helperText`, and each option is the `Checkbox` of the library. Props: `options` (`{ value, label, disabled? }`), `label`, `name`, `value` and `defaultValue` (lists of strings), `onValueChange` (gets the whole list of checked values, in the order of the options, at every check and uncheck; a disabled option that is checked stays in the list), `error`, `helperText`, `orientation` (`vertical`, the default, or `horizontal`), `animation` and the attributes of the `<fieldset>`. There is no `required`: HTML has no "check at least one", so the group does not pretend; validate in the form and pass `error`. Tab walks the boxes and Space checks, with no arrow keys, as with a native checkbox. Every box gets `aria-invalid` when there is an `error`, and with `name` each checked value is sent with it. A `Checkbox` with `aria-invalid="true"` now draws the border of its unchecked box in the error color (`--enchase-checkbox-box-border-color-invalid`, `--enchase-color-error` by default). Hooks `--enchase-checkbox-group-*`.
- `Checkbox`: a label with a long word with no spaces (`Benachrichtigungseinstellungsverwaltungsseite`) pushed its container wide (395 px in one of 140 px), because the label of an `inline-flex` did not wrap. It wraps now, with the same three declarations that the `RadioGroup` already had; nothing changes for text that fits.
- `SegmentedControl` is a row of connected buttons to switch between a few options of the same kind. It chooses one by default (`role="radiogroup"` with `role="radio"` buttons and `aria-checked`) and, with `multiple`, it is a `role="group"` of toggle buttons with `aria-pressed`; it is never a `tablist`, since nothing here swaps a panel (that is what `Tabs` is for). Props: `items` (`{ value, label, ariaLabel?, disabled? }`, where `label` can be nodes), `ariaLabel` or `aria-labelledby`, `multiple`, `value`, `defaultValue` and `onValueChange` (a string, or a list of strings with `multiple`: the type is a union discriminated by `multiple`), `size` (`sm`, `md`, the default, or `lg`, as tall as a `Button` of the same size), `fullWidth`, `disabled` and `animation`. In the single mode there is one Tab stop (the checked option, or the first enabled one when none is checked) and the four arrow keys move and check, with wrap-around (left and right swap in right-to-left pages), Home and End go to the ends, disabled options are skipped and clicking the checked one does nothing and tells nobody. With `multiple`, Tab walks every button, Space and Enter toggle and the arrows do nothing. `onValueChange` gets the value that was just checked, or the list of the pressed ones in the order of the items. The checked option is filled with `secondary-container`, and in forced colors it becomes `Highlight`. Hooks `--enchase-segmented-control-*`.
- `Slider` picks one number in a range, by dragging the thumb, clicking the track or with the keyboard. It is a `role="slider"` with `aria-valuemin`, `aria-valuemax` and `aria-valuenow`, and `aria-valuetext` only when you pass `formatValue`; there is no range with two thumbs. Props: `value`, `defaultValue`, `onValueChange`, `min` (0), `max` (100), `step` (1, fractions accepted), `label` (the visible name), `ariaLabel`, `formatValue`, `showValue` (the number beside the label, hidden from assistive technology), `name` (a hidden field for forms; a disabled slider does not send it, as a native control does), `disabled` and `animation`. The value shown is the stored one rounded to the step from `min` and held at the last step that fits before `max`, with no floating-point residue (0.1 + 0.2 is 0.3): a value out of the range, off a step or `NaN` never reaches the DOM, and `onValueChange` gets the normalized value and only when it changes. The arrow keys move one step (up and right add), PageUp and PageDown a tenth of the range, Home and End the ends; in right-to-left pages left and right swap and the track fills from the right. A mouse or a pen moves the value at the pointer down and follows the drag outside the control; a finger only moves it with a short tap (applied when it lifts) or when it travels more than 6 px across without going further along the page, so a vertical swipe that starts on the slider scrolls the page and changes nothing (`touch-action: pan-y`). The thumb takes the focus by script on a click, and its ring only shows for the keyboard. The control is as tall as the hit size (40 px by default, never less than 24) and as wide as its box. In forced colors the track is an outline in `CanvasText`, the filled part is solid `CanvasText` and the thumb is a circle outlined in `CanvasText`. Hooks `--enchase-slider-*`.
- `Table` gets four optional things and nothing else changes for whoever does not use them. `header` of a column is a `ReactNode` now (it was a `string`; a column that sorts keeps it inside a button, so it cannot hold a button or a link). A column with `sortable` gets a button in its header; `sort` (`{ key, direction }`, with the new type `TableSort`) says how the rows are ordered and `onSortChange(sort)` is called with the sort that was asked for: ascending for a column that is not sorted and the other direction for the sorted one, with no state to clear it. The table does not order anything: the app orders `rows` and passes the new `sort` back. `aria-sort` goes on the header of the column whose key is `sort.key`, with a button or not, and nowhere else; the indicator shows the direction, comes before the text in an `end` column so that the text lines up with the numbers, and mirrors in right-to-left pages. The README has a new section, "Listas e cartões clicáveis", `API.md` has the new props and the new CSS hook, and the Storybook has 17 new stories. Besides what is listed below, nothing changed at runtime with the default style.
- `as` takes one of the structure tags: `div` (the default), `section`, `article`, `aside`, `nav`, `header`, `footer`, `main`, `ul`, `ol` or `li`. The list is closed on purpose. It has no `span` and no interactive tag, since a link or a button is a `CardLink`, a `CardButton` or a `ButtonLink`, and a tag can be added later without breaking anyone, while removing one could not. With `ul` or `ol` the root also gets `role="list"`, because Safari with VoiceOver drops the list semantics of a list whose markers are removed with CSS; a `role` you pass wins. The root of the four components now has `list-style: none`, so a list made with them has no marker, margin or indent of its own, and the browser tests check, in Chromium, Firefox and WebKit, that the root of each one has the box of a `div` when it is a `ul` or an `ol`, and that a `ul`, an `ol`, their items and a `summary` inside it keep their markers. The props of the four are now typed as `HTMLAttributes<HTMLElement>` and not `HTMLAttributes<HTMLDivElement>`: a handler typed for `HTMLDivElement` still compiles (the consumer test has one), and the only difference for TypeScript is that the `currentTarget` of a handler written inline is an `HTMLElement`. A list of badges is a `Flex as="ul"` with `wrap` and a `Badge` in each `li`, and a list of cards is a `Grid as="ul"` with a `Card as="li"`, or a `CardLink` inside a `li`, in each cell.
- `CardButton` and `CardLink` are a `Card` that is one click target. `CardButton` renders a `<button type="button">`, which never submits a form on its own, and takes the props of a button. `CardLink` renders an `<a>` with a required `href` and follows the rules of the `Link`: a route of the app goes through the `navigate` of the `UIProvider`, `native`, `target` and `download` leave the click with the browser, and `target="_blank"` adds `rel="noopener noreferrer"` and a visually hidden "opens in a new tab" text to the accessible name, with no icon. The text of a `CardLink` keeps the color it inherits, visited or not, with no underline. Both take the `variant`, `padding` and `animation` of the `Card` and read the same CSS hooks, `--enchase-card-*` (the `data-slot` is `card-button` or `card-link`), so a style that redraws the `Card` redraws them, and both add what a control needs: the focus ring, the hover and pressed layers of the `--enchase-state-*` tokens, a pointer cursor and a target of at least 24px. A tile fills the width and the height of its cell, so tiles with different content line up in a `Grid`, and the `elevated` variant lifts on hover as the `Card` does. A disabled `CardButton` fades with the new hook `--enchase-card-opacity-disabled`, which follows `--enchase-state-disabled-content` (`0.38`) by default and which the `shadcn` style sets to `0.5`. Everything inside a tile is part of its accessible name, so keep it short, and put no other link, button or field inside it.
- `AccordionItem.title` and `TabsItem.label` are `ReactNode` and were `string`, so an item can have a logo, an icon or a `Badge` next to its text. A string works as before. The title is inside the `<button>` of the trigger and the label inside the `<button>` of the tab, so they take text-level elements only, with no other button, link or field, and everything in them is part of the accessible name of the button and of its panel (a decorative image takes `alt=""` or `aria-hidden`). For TypeScript, code that reads `title` or `label` back from a typed list of items and uses it as a string now has to narrow it.
- The pressed layer now wins over the hover layer. In 0.8.0 the `Button`, the `ButtonLink`, the controls of the `Pagination`, the tabs of the `Tabs` and the triggers of the `Accordion` showed the hover value of their state layer while the mouse was down (`--enchase-state-hover`, 8%) and not the pressed one (`--enchase-state-pressed`, 10%), because a mouse press matches `:hover` and `:active` at once and the hover rule came later in the CSS with the same specificity. A touch press showed the pressed value, since the hover rules only apply to a fine pointer. The `Button` had the same problem with the layer of the keyboard focus when the pointer was over the focused button. The pressed and focus rules now come after the hover rule, with the same specificity, in those components and in the new tiles. With the default tokens the layer goes from 8% to 10% on a mouse press (a theme that sets the two tokens further apart shows a bigger change), and nothing changes on touch. A new test reads the CSS of every component and fails when a pressed or focus rule comes before the hover rule of the same element and property; on the CSS of 0.8.0 it finds the `Button`, the `Pagination`, the `Tabs` and the `Accordion`, and no other component.
- With the default style the look is the one of 0.8.0 apart from that. A computed-style audit of the 212 stories of the Storybook (the 195 of 0.8.0 and the 17 new ones), in Chromium, Firefox and WebKit, in the light and dark modes and in the hover, pressed, focus and tab states, found in the old stories only the change above: 245 times in each browser, always the opacity of the layer of a `Button`, `ButtonLink`, `Pagination` control, `Tabs` tab or `Accordion` trigger while it is pressed, from `0.08` to `0.1`. The only other change in the computed style of the old stories is `list-style-type`, which the audit does not read: it is `none` on the root of the four components, where it was `disc` and nothing was drawn.
- Weight: with the default style, `enchase/styles.css` goes from 17.4 to 17.6 kB gzip (149.3 to 150.9 kB raw), with the CSS of the two tiles, and `enchase/theme.css` and the bundle of the `ColorModeProvider` do not change. ### Notes

- New: visual styles, with the `shadcn` one included (`style` in `createTheme` and in the `theme` prop of the `ColorModeProvider`); `defineStyle`, to write a style of your own; the `labelPlacement` prop on the fields; theme tokens for the focus ring, the borders, the state layers, the halo, the target sizes, the line heights and the letter spacings; and CSS hooks that restyle the space, the size, the color, the shadow and the type of every component. Besides what is listed below, nothing changed at runtime with the default style.
- `createTheme` takes `style`, and so does the `theme` prop of the `ColorModeProvider`. A style is an object that changes the look of the whole kit at once: the palette, the corners, the heights, the weights, the borders, the shadows and the place of the label of the fields. Without `style` the look is the one of always (the `enchase` style, which changes nothing). What you pass wins over the style, in this order: the defaults of the library, the style, then `shape`, `radius`, `fonts`, `motion`, `brand`, `light` and `dark`. With `brand`, only the accent of the style changes (the `primary` color and what derives from it) and the neutrals stay. A style is made of tokens and CSS hooks that the `ColorModeProvider` writes on `:root` and in the block of each color mode, so the CSS of your app still wins over it. The `ThemeSet` that `createTheme` returns has two new optional keys, `hooks` and `defaults`, so a `ThemeSet` written by hand keeps working, and `ThemeInput` has the new `style` key.
- Each style has its own entry, `enchase/styles/<name>`: `enchase/styles/shadcn` and `enchase/styles/enchase`, as in `import { shadcn } from 'enchase/styles/shadcn'`. A style is only data, with no React, so it works in a Server Component: import it in the server layout and pass it to the `ColorModeProvider`. The entries are separate files of the package, so an app pays only for the styles it imports, even with a bundler that does not drop dead code, and a style can be loaded on demand with `import('enchase/styles/shadcn')`. There is no `enchase/styles` alone on purpose, since the CSS is `enchase/styles.css`: forgetting the `.css` is an error and not an import that does nothing. A style given by name (`style: 'shadcn'`) throws an error that says which import to use.
- The `shadcn` style brings the kit closer to shadcn/ui: a neutral palette, borders instead of shadows, buttons and fields of 36px with 14px text, corners of `0.5rem`, neutral alerts with a colored icon and title, tinted badges, tabs with only the underline, a flat accordion and the label above the field. It is inspired by it, not a copy, and the accessibility contract of the library comes first: the border of the fields and the track of the switch when off are `#808080` (3:1 against the background; the original has 1.26:1), the focus ring is solid, 2px, in the `primary` color, with 2px of offset (the original uses a translucent ring), the secondary text on the gray surfaces and the error red used as text have 4.5:1, the targets keep at least 24px, the fields have 16px text on touch devices, and in forced colors (the Windows high contrast mode) the focus border of the fields is at least 2px, whatever the style, because the ring made with a shadow disappears there. `validateTheme` finds nothing wrong in it, with or without `brand`, and the tests run an `axe` contrast check of the whole kit in both color modes, in the three browsers.
- `defineStyle`, from `enchase/theme`, is how you write a style of your own. It takes an object with the sections `base` (the `control`, `focus`, `border`, `halo`, `hit` and `state` tokens), `fonts` (`sizes`, `weights`, `lineHeights` and `letterSpacings`), `radius`, `hooks`, `colorHooks`, `light` and `dark` (each with `colors`, `shadows` and `hooks`), `brand` (which roles of the palette come from the brand color) and `defaults`; it checks the object, says which part is wrong and returns it frozen. It throws for an unknown section or token, for a CSS value that is not safe (with `;`, `{`, `}`, `<`, `>`, a backslash, a comment, `url()`, `@import`, an unbalanced parenthesis or quote, or more than 400 characters), for a hook name that is not `--enchase-` followed by lowercase words, for a "hook" that is a theme token, and for a root hook that cites a color or a shadow of the theme (that one goes in `colorHooks`, or in `light.hooks` and `dark.hooks`). `createTheme` checks again a style that did not come from `defineStyle`, because a style can arrive as JSON or across the boundary of a Server Component. The contrast of the colors is not checked by `defineStyle`: run `validateTheme` on the result. The types `ThemeStyle`, `ThemeStyleMode`, `HookValues`, `LabelPlacement` and `ThemeDefaults` are exported by `enchase/theme`, and the README has a section on writing a style.
- `Input`, `Textarea`, `NumberInput` and `Select` take `labelPlacement`: `floating` (the default of the `enchase` style) keeps the label inside the field, and it goes up to the outline when the field is focused or filled; `stacked` (the default of the `shadcn` style) puts the label above the control, with no notch in the outline and the helper text and the error below. The prop wins over the style, in both directions, and without a `ColorModeProvider` the label floats. The `<label>` comes before the control in the HTML in both placements, the same on the server and on the client, so there is no hydration mismatch.

The values are the ones the components had written in their CSS, so the default look does not change. One consequence for TypeScript: `BaseTokens` gained the keys `focus`, `border`, `halo`, `hit`, `fonts.lineHeights`, `fonts.letterSpacings`, `state.rowHover`, `state.disabledContainer` and `state.disabledContent`. `createTheme` fills them in, but a `BaseTokens` object written by hand needs them.
- Each component reads optional CSS hooks named after the `data-slot` of the part and the property, `--enchase-<data-slot>-<property>`, with the size or the variant when there is more than one (`data-slot="switch-thumb"` and `size` give `--enchase-switch-thumb-size`). The full list, with the default and the property of each hook, is in `API.md` and is generated from the CSS of the components, so it does not go out of sync. It is an `<input type="text">` with `role="spinbutton"` and a numeric keyboard on phones, not `type="number"`: the text follows the language of the `UIProvider` (a comma for decimals and a dot for thousands in `pt-BR`, the opposite in `en`) and the value comes out as a `number`, or `null` when the field is empty. It takes `value`, `defaultValue` and `onValueChange(value)`, `min`, `max`, `step` (1 by default), `largeStep` (ten times `step` by default), `formatOptions`, `steppers` (`true` by default), `name`, `form`, `wrapperClassName` and `wrapperStyle`. `className`, `style`, the other attributes and the `ref` go to the `<input>`.
- The value is confirmed when the field loses the focus, with Enter, with the arrow keys and with the buttons, never on each key. What was typed is read the way the locale writes numbers (`1.234` in `pt-BR` is a thousand two hundred thirty-four, and `1.5` is one and a half), held between `min` and `max` and rounded to the digits of the format. Letters are refused as they are typed, and so is the minus sign when `min` is 0 or more. The arrows change the value by `step`, Shift with them and Page Up and Page Down by `largeStep`, and Home and End go to `min` and `max`. Steps count from `min` (or 0), so a step of 100 from 1235 goes to 1200. From an empty field, the up arrow goes to `min` (or 0) and the down arrow to `max` (or 0).
- `formatOptions` takes part of `Intl.NumberFormat`: `style` (`decimal`, `currency` or `percent`), `currency`, `currencyDisplay`, `minimumFractionDigits`, `maximumFractionDigits` and `useGrouping`. Without `maximumFractionDigits`, the digits of the style apply (3 for decimals, 2 for currency, 0 for percent) or the ones the `step` asks for. A percentage is the fraction: 0.15 shows as 15%. The currency symbol may be typed or left out, and a language tag that `Intl` does not accept falls back to English. The type is exported as `NumberInputFormat`. With `name`, the number goes to the form through a hidden input as a plain `1234.5`, never with the formatting of the screen.
- The buttons of the `NumberInput` are out of the tab order, because the keyboard already has the arrows, and holding one repeats the step. A polite live region announces the new value when a button is used. On iPhone the numeric keyboard has no minus key: pass `inputMode="text"` to accept negative numbers. The field reads `--enchase-number-input-duration` and `--enchase-number-input-ease` for its motion, listed in the Movimento table of the README. No other theme token was added.
- Two keys were added to `UILabels`, both optional: `increaseValue` and `decreaseValue` (the names of the buttons of the `NumberInput`). They are optional so that a `Locale` of your own, written before this version, still type-checks. The `en` and `ptBR` locales define them, and a locale or a `labels` object that leaves them out falls back to the English text. `useUIConfig()` also returns `locale` now, the language code of the `UIProvider` locale (`pt-BR`, `en`), which is `en` without a provider. The `NumberInput` formats and reads numbers with it, and it can feed your own `Intl` calls.
- New entry `enchase/icons`, with the 19 icons the components use inside, one component per icon: `AlertTriangleIcon`, `CheckIcon`, `ChevronDownIcon`, `ChevronLeftIcon`, `ChevronRightIcon`, `ChevronsLeftIcon`, `ChevronsRightIcon`, `CloseIcon`, `ExternalLinkIcon`, `EyeIcon`, `EyeOffIcon`, `InfoIcon`, `LogOutIcon`, `MenuIcon`, `MenuOpenIcon`, `MinusIcon`, `MoonIcon`, `PlusIcon` and `SunIcon`, plus the `IconProps` type. A test keeps the list equal to the icons the components import, so an icon is only added when a component starts to use it. This is not an icon library: for other icons, use one (lucide-react, Phosphor, Heroicons) or the `Icon` container of `enchase` with your own paths.
- Each icon takes `size` (24 by default), `title` and the attributes of an `<svg>`, and is drawn with `currentColor`. Without a `title` it is decorative (`aria-hidden`); with one it becomes an image with an accessible name, and a button with only an icon still needs an `aria-label`. `data-icon` holds the name in kebab case (`chevron-left`). The seven icons that point somewhere (`ChevronLeftIcon`, `ChevronRightIcon`, `ChevronsLeftIcon`, `ChevronsRightIcon`, `ExternalLinkIcon`, `LogOutIcon` and `MenuOpenIcon`) mirror in right-to-left text.
- `enchase/icons` is not marked `'use client'`, so a Server Component can import it (the Next 15 app of the tests renders them on the server), and each icon is its own module, so a bundler keeps only the ones you import: one icon costs about 0.9 kB gzip and all 19 about 1.6 kB. The Storybook has a gallery in the story of the `Icon`. Changing how an icon is drawn is not a breaking change; renaming or removing one is.
- `ButtonLink` takes `externalIcon` (`true` by default). With `target="_blank"` the link shows the external link icon after the text, as before; `externalIcon={false}` removes only the icon and keeps the "opens in a new tab" text for screen readers (`labels.opensInNewTab`). In a link with only an icon and an `aria-label`, put the notice in the label.
- `useScrollSpy` used to keep the elements it found when it mounted, so a section that mounted later or was replaced by a new element with the same `id` was never watched, and the highlight stayed wrong. It now follows the page: a section that mounts later or remounts is watched, one that leaves the page is dropped, and the active `id` is cleared when its section is gone. Only the content of the `ids` array counts, not its identity, so an array written inline does not restart the observer.
- A label longer than the field no longer pushes the notch of the outline of the `Input`, `Textarea` and `Select` past the field: the notch stops at the width of the field.

## v0.1.0

First public release of Enchase, a set of accessible React 19 components with no runtime dependency besides React. While the version is `0.x`, the API may still change between minor versions.

### Highlights

- Components: Button, ButtonLink, Link, Icon, Input, Select, Checkbox, Card, Modal, ConfirmModal, Popover, Tooltip, Toast, Loading, InlineLoading, Skeleton, Sidebar, Navbar, Layout, Breadcrumbs, Footer, Container, Flex, Grid, ThemeToggle and VisuallyHidden.
- Theme with validated contrast: `createTheme` and `validateTheme` in `enchase/theme`, light and dark, and a static `theme.css` for the default theme.
- CSS first: the component styles in `styles.css`, the same rules inside `@layer enchase` in `styles.layer.css`, and the `className` of the caller always wins over the library.
- Motion built in CSS, with spring tokens and `prefers-reduced-motion` support, and no animation library.
- Server rendering and React Server Components (proved with a Next 15 app), RTL, and the `en` and `ptBR` locales in `enchase/locales`.
- Bootstrap 5 breakpoints with `UIProvider breakpoints` and `useBreakpoint`.
- One file per module and `sideEffects` only for CSS, so a bundler drops what is not imported.
