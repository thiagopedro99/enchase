# skill.md — enchase code conventions

Convenções de código do template. Prioridade absoluta: consistência com o padrão já existente no projeto — evite reinventar a roda ou introduzir abstrações não pedidas explicitamente.

## Estilo de código

- Sem ponto e vírgula no fim das instruções.
- Aspas simples em strings e imports.
- Imports locais com a extensão do arquivo (`'./types.ts'`, `'../Button/index.tsx'`).
- Linha vazia antes do `return` quando a função tem mais de uma instrução.
- **Nunca comentar código** — sem `//`, `/* */`, `{/* */}` nem comentário dentro dos arquivos `.module.css`. Nem cabeçalho com o caminho do arquivo. O nome claro do componente/função/variável é a documentação. Exceção: diretivas funcionais (`/// <reference ... />`) e texto de exemplo exibido ao usuário (strings de código nas páginas de documentação).

## Formatação e indentação

Linha única **apenas** para:
- Importações: `import { A, B, C } from 'x'`
- Desestruturação de hooks: `const [value, setValue] = useState(false)`
- Declaração de componentes/funções simples: `const MyComponent = () => {label}`
- `if` de retorno antecipado sem bloco: `if (!value) return null`

Sempre indentado (nunca em linha única):
- Blocos de JSX com mais de um elemento filho
- Objetos e arrays com mais de uma propriedade/item
- Funções com corpo `{}` contendo mais de uma instrução
- Ternários com expressões longas (3 linhas: condição, `?` valor, `:` valor)
- Chamadas encadeadas (`.map`, `.filter`, `.reduce`) com callbacks multilinhas
- `if/else` com blocos `{}`
- `return` de JSX com mais de um nível de aninhamento

Regra geral: se o conteúdo não cabe legível em ~100 caracteres, indente. Compacto significa sem linhas vazias desnecessárias, não significa ausência de indentação.

## Imports

- Sempre em linha única — proibido quebrar linha dentro de `import { A, B }`; deixe a linha longa se necessário.
- 3 blocos separados por 1 linha vazia: bibliotecas externas > módulos internos > `import type`.
- Dentro de cada bloco, ordene do import mais longo (mais caracteres) para o mais curto.
- Remova imports não usados; o código não deve compilar com imports sobrando.

## Componentização (obrigatório)

- `index.tsx` de uma página é só orquestrador de estado e layout — não contém blocos complexos de JSX.
- Divida a UI em seções lógicas (Header, Filters, List, Footer...), cada uma em pasta própria sob `/subcomponentes`, seguindo o padrão de 3 arquivos: `index`/`styles`, `types` (obrigatório em TS), `defaultData` (se necessário).
- Todo valor padrão de prop mora no `defaultData.ts` do componente como `defaultNome` (ex.: `defaultVariant`, `defaultSize`), e o componente e os estilos usam essa constante em vez de escrever o valor no código. A story do componente importa a mesma constante para `args` e para a coluna de padrão da tabela de props. Prop sem padrão não ganha constante.
- Nunca entregue uma página monolítica: se o JSX passar de ~100 linhas, extraia.
- `/components` é só para itens reutilizados em múltiplas páginas.
- Sem estilos inline — sempre em `styles.module.css` (ver seção Estilos). Exceções: valores dinâmicos passados como variável CSS (ver seção Estilos) e valores dinâmicos de `motion` (ver seção Animação).
- Sem `console.log`, `console.debug` nem `console.info`: a regra `no-console` do ESLint só libera `console.warn` e `console.error`. No build, `console.log` e `console.debug` também são removidos (`treeshake.manualPureFunctions` no `vite.config.ts`), e `warn` e `error` ficam.
- Proibido `import React from 'react'` (JSX transform é padrão); importe só o que usa (`{ useState }` etc).

## Estilos (CSS Modules)

- CSS Modules é o único mecanismo de estilo: cada componente tem um `styles.module.css` ao lado do `index.tsx`, importado como `import styles from './styles.module.css'`. Sem CSS-in-JS e sem biblioteca de UI.
- Classes combinadas com `classNames` de `@utils/classNames.ts`: `className={classNames(styles.button, className)}`. O componente sempre aceita e mescla o `className` de quem usa.
- Variantes e tamanhos (valores de lista fixa) viram atributos `data-*` no elemento (`data-variant`, `data-size`; booleano por presença do atributo, como `data-full-width`), e o CSS usa seletor de atributo (`.button[data-variant='outline']`). A prop pública tem nome simples (`variant`, `size`, `fullWidth`), nunca com `$`, e não é repassada ao DOM.
- Valores livres (largura, número de colunas, tamanho calculado) passam por variável CSS inline (`style={{ '--grid-template-columns': value }}`), declarada e usada no `.module.css`. Fora isso, só valores do `motion` ficam em `style`.
- Estados por pseudo-classe e atributo ARIA (`:hover`, `:focus-visible`, `:disabled`, `[aria-invalid='true']`), não por prop espelhada.
- Valores do tema só por variáveis CSS `--enchase-*`: cores (`--enchase-color-*`, aninhadas em kebab: `text.primary` vira `--enchase-color-text-primary`), `--enchase-shadow-*`, fontes (`--enchase-font-primary`, `--enchase-font-size-*`, `--enchase-font-weight-*`), `--enchase-space-*`, `--enchase-radius-*`, `--enchase-transition-*`, `--enchase-state-*` e `--enchase-z-*`. Nunca hex, `rgba` nem espaçamento de tema soltos. Medidas próprias do componente (altura de um botão, por exemplo) podem ser literais.
- Breakpoints não têm variável (media query não aceita `var()`): use o valor literal no CSS, igual ao de `breakpoints` em `src/styles/tokens/base.ts`. Em JS, importe `breakpoints` de `@styles/tokens/index.ts`.
- O tema mora em `src/styles/`, dividido em `tokens/` (dados), `theme/` (construção e validação: `createTheme`, `validateTheme`, validadores) e `css/` (geração das variáveis e do CSS global), mais `react.tsx` (`GlobalStyles` e `ThemeVariables`). `tokens` não importa nada; `theme` e `css` só importam de `tokens`; só `react.tsx` usa React. `styles/index.ts` reexporta tudo menos o React e os estilos, mas só o que está listado por nome em `lib/theme.ts` é público (o `entries.test.ts` confere a lista exata, valores e tipos): nada de `export *` ali, e abrir um helper do `src/styles/` para quem consome é uma decisão que entra nessa lista e no README. Os estilos (`presets/`) são dado puro e ficam fora do núcleo: só os arquivos de `lib/styles/` os exportam (`enchase/styles/<nome>`, uma entrada por estilo e nenhuma em `enchase/styles` sozinho, para que esquecer o `.css` de `enchase/styles.css` dê erro em vez de um import que não faz nada), e nada do `src/` os importa fora dos testes, para que quem não usa um estilo não pague por ele (o ESLint, o `styleIsolation.test.ts` e o `checkPackage.mjs` travam isso). O ESLint trava essas dependências (`no-restricted-imports` em `eslint.config.js`), e dentro de `src/styles/` os imports são relativos, nunca pelo alias `@styles/*`. Mudar um token é mudar `tokens/`: as variáveis saem sozinhas.
- Tema do usuário entra por `<ColorModeProvider theme={...}>` no formato de `createTheme`. Todo valor de cor, família, tamanho e peso passa por validador (`isValidColor`, `isValidFontFamily`, `isValidFontSize`, `isValidFontWeight`) antes de virar CSS; nunca interpolar valor de tema sem validar.
- O modo de cor (`light`, `dark` ou `system`) vem do `ColorModeProvider`; leia e troque com `useColorMode()` e nunca guarde o tema em um store. O `data-theme` do `<html>` troca os valores das variáveis, então os componentes não conhecem o modo.
- Nome da classe reflete o elemento semântico (`.container`, `.header`), não o estilo (`.blueBox`).

## Componente pronto (checklist)

- Pasta com `index.tsx`, `styles.module.css`, `types.ts` e, se houver valor padrão, `defaultData.ts`.
- Props públicas sem `$`, aceitando e mesclando `className`.
- Variantes por `data-*` e valores do tema por `var(--enchase-*)`.
- Animação por CSS com `usePresence` e a prop `animation`; textos de acessibilidade por `useUIConfig().labels`.
- Teste de comportamento e `axe` espelhado em `src/tests/`.
- Story com Playground em `src/docs/stories/`, com as descrições das props em `argTypes`.
- Texto da documentação em inglês (descrições das stories e das `argTypes`, páginas `mdx`, gerador do `API.md`, `README.md`, `CONTRIBUTING.md`, `llms.txt`), com os termos de `scripts/docsGlossary.json`. O `docsLanguage.test.ts` falha se algum desses arquivos tiver português, então arquivo novo já nasce em inglês. Os dados de exemplo das stories também ficam em inglês, exceto numa demonstração que existe para mostrar o `ptBR`. O `README.pt-BR.md` é o guia em português e fica de fora.
- Conferido no navegador nos dois temas.

## Linguagem visual (Material Design 3)

- O visual segue o Material Design 3 implementado só com CSS Modules e variáveis CSS. Nunca usar a biblioteca MUI.
- Cor sempre por papel do tema (`primary`, `primaryContainer`, `surfaceContainer*`, `on*`, `inverse*`, `error`...); proibido hex ou `rgba` solto em `.module.css`; use `var(--enchase-color-*)`. Texto sobre um papel usa o `on*` dele.
- Camadas de superfície: página em `surface`/`background`; cards, barras e diálogos em `surfaceContainerLow`, `surfaceContainer` ou `surfaceContainerHigh`. Elevação por `shadows` só em elementos que flutuam (elevated card, menus, diálogos).
- Hover, foco e pressionado por camada de estado: pseudo-elemento `::after` com `currentColor` e opacidade `var(--enchase-state-hover)` ou `var(--enchase-state-pressed)`, ou `color-mix(in srgb, <cor> calc(var(--enchase-state-hover, 0.08) * 100%), transparent)` com o token do estado (`hover`, `pressed`, `row-hover`, `disabled-container` ou `disabled-content`); não trocar a cor para escurecer, e nenhuma porcentagem de estado escrita no componente.
- Variantes de botão: `primary` (preenchido), `secondary` (tonal), `outline` e `ghost` (texto). Formas por `--enchase-radius-*`: botões, itens de menu e badges `button` (o papel que um preset de forma troca, por padrão a pílula `full`), campos `control`, cards `xl`, diálogos `2xl`. `full` fica só para o que precisa ser redondo em qualquer preset (chave, bolinha do radio, avatar); o teste `radiusRoles` lista onde ele ainda aparece.
- Tipografia: fonte `var(--enchase-font-primary)` (Figtree, importada em `demo/main.tsx`); títulos com peso `medium`.

## Estilos visuais (`createTheme({ style })`)

- Um estilo é só dado: `src/styles/presets/<nome>.ts` faz `export const <nome> = defineStyle({ ... })` (`defineStyle` vem de `../theme/style.ts`; as seções são `base` com os tokens `control`, `focus`, `border`, `halo`, `hit` e `state`, `fonts`, `radius`, `hooks`, `colorHooks`, `brand`, `light`, `dark` e `defaults`), e `lib/styles/<nome>.ts` reexporta só ele (`export { <nome> } from '../../src/styles/presets/<nome>.ts'`). O estilo chega ao `createTheme` como objeto (`createTheme({ style: shadcn })`), nunca por nome, e não há registro: importar o estilo é o que o põe no bundle. O `enchase` é o padrão vazio. O preset só importa `defineStyle` e tipos de `tokens` (nem React, nem outro preset). Nenhum componente conhece um estilo: tudo que um estilo muda chega por token, por gancho ou por `defaults`.
- A precedência do `createTheme` é: padrão da biblioteca, depois o `style`, depois o que o usuário passa (`shape`, `radius`, `fonts`, `motion`, `brand`, `light`, `dark`). Com `brand`, só os papéis listados em `brand` do estilo vêm da cor (o acento); os neutros ficam do estilo.
- O contrato do `defineStyle` (`src/styles/theme/style.ts`, com os valores seguros em `cssValue.ts`) vale para qualquer estilo, de dentro ou de fora: seções e tokens conhecidos; nome de gancho `--enchase-<palavras-em-kebab>` que não seja um token; valor sem `;`, `{`, `}`, `<`, `>`, `\`, comentário, `url()`, `@import`, parêntese ou aspas sem fechar, e com até 400 caracteres; e gancho da raiz sem `var(--enchase-color-*)` nem `var(--enchase-shadow-*)`. O `createTheme` confere de novo o que não saiu do `defineStyle` (um JSON, ou um estilo que atravessou a fronteira de um Server Component). Mudar uma regra é mudar `style.ts` e `style.test.ts`.
- Um gancho de um estilo precisa existir no CSS dos componentes e não pode ser um token do tema (o contrato de `presets.test` confere os dois em todo estilo embutido). Gancho de medida, tipografia, sombra e opacidade vai em `hooks` (declarado no `:root`); gancho que cita um papel de cor (`var(--enchase-color-*)`) vai em `colorHooks` ou em `light.hooks` e `dark.hooks`, que o `themeCss` declara dentro dos seletores de modo.
- Capacidade que só um estilo usa (borda do alerta e do diálogo, sombra do contorno do campo, opacidade de desabilitado, cor do ícone e do título do alerta) entra no componente com um padrão que não muda o visual: largura `0` com cor `transparent` (`border: var(--enchase-alert-border-width, 0) solid var(--enchase-alert-border-color, transparent)`), sombra `none`, `inherit` para cor e tamanho herdados, opacidade `1`. A auditoria de estilos computados do `enchase` tem que continuar sem diferença, fora a borda de largura zero, que muda só o `border-style` e a cor de uma borda que não aparece.
- Um estilo não rebaixa os pisos de acessibilidade: área de toque de 24px ou mais (`max(24px, var(--enchase-hit-size, ...))`), fonte de 16px nos campos com ponteiro de toque, contraste AA (`validateTheme` sem pares reprovados, com e sem `brand`, e o `axe` do navegador sem violação nos dois modos), foco visível por `outline` (que o modo de cores forçadas mantém) e, nos campos, a borda em foco com 2px ou mais em cores forçadas. Onde a referência visual reprova (borda de campo, anel de foco, texto secundário), o estilo ajusta o valor e a diferença vai para o `README.pt-BR.md`.
- O lugar do rótulo dos campos (`labelPlacement`: `floating` ou `stacked`) é estrutural, então é prop, e o padrão vem do contexto do tema (`useThemeDefaults`). No `stacked` o `<label>` vem antes do controle no HTML e o CSS fica em `.wrapper[data-label-placement='stacked'] > .label`, sem entalhe no contorno; o `floating` não muda. A ordem no HTML é a mesma no servidor e no cliente.
- Ao pôr um estilo novo: o arquivo em `presets/`, o `lib/styles/<nome>.ts`, a entrada `./styles/<nome>` nos `exports` do `package.json` (`types` em `dist-lib/types/lib/styles/<nome>.d.ts`, `import` e `default` em `dist-lib/styles/<nome>.js`), a linha `'styles/<nome>'` nas entradas de `vite.lib.config.ts` e a entrada em `src/tests/shared/fixtures/styles.ts` (o `styleIsolation.test.ts` falha se faltar uma delas, o `checkPackage.mjs` falha se o estilo construído não tiver exportação, e os contratos passam a rodar no estilo sozinhos: o de `presets.test.ts` (as mesmas variáveis do tema padrão, contraste AA com e sem `brand`, pisos de acessibilidade, ganchos que existem e não são tokens, emissão e precedência) e o de `styleContract.spec.tsx` nos três navegadores (contraste do `axe` nos dois modos, com e sem `brand`, e nos diálogos, alvos de 24px e anel de foco de 2px), mais o texto de 16px nos campos com ponteiro de toque em `touch.spec.tsx`, que roda isolado porque a emulação de toque vale para a página inteira, o bloco do estilo em `presets.test.ts` (os valores dele), um spec de navegador no molde de `shadcnStyle.spec.tsx` (valores computados dos componentes, foco, cores forçadas), a story em `System/Styles` e a opção em `src/docs/shared/styles.ts`, que alimenta a barra de ferramentas do Storybook. Um estilo não pesa para quem não o importa: `testBundleSize.mjs` (orçamentos e ganchos do estilo ausentes do núcleo) e `checkPackage.mjs` (só `enchase/styles` alcança `presets/`) conferem, e o orçamento do estilo novo entra em `testBundleSize.mjs`.

## Layout e navegação

- Páginas sempre dentro de `Layout` (`@components/layout`). A navegação padrão é `navigation="sidebar"`; `navigation="navbar"` usa a barra superior. Nunca montar `Sidebar` ou `Navbar` direto em uma página.
- Itens de menu vêm de `SidebarSection[]`: rota com `href` (`/caminho`), âncora com `href` (`#id`) e ação com `onClick`. Seções específicas da página entram por `pageSections`, com `activePageSectionId` vindo de `useScrollSpy`.
- O `Sidebar` é um componente reutilizável com duas variantes (`permanent` e `modal`) e estado recolhido controlado por quem o usa. No `Layout`, o estado recolhido (`collapsed`, `defaultCollapsed`, `onCollapsedChange`, `storageKey` opcional) e a abertura do drawer (`open`, `defaultOpen`, `onOpenChange`) são controlados ou não; o botão que recolhe e abre o menu mora na `AppBar` do `Layout`, não no rodapé da sidebar.
- A `AppBar` do `Layout` reúne botão de menu, `Breadcrumbs` e ações (tema). O botão de menu usa `MenuToggleIcon` (ícone de menu aberto quando expandido, hambúrguer quando fechado, com troca animada) e um `Tooltip` com `describe={false}` repetindo o rótulo da ação atual. A trilha vem da prop `breadcrumbs` ou é derivada do menu e da rota (`deriveBreadcrumbs`); o último item é sempre a página atual, sem link.
- `header` e `footer` do `Sidebar` aceitam um nó ou uma função `({ collapsed }) => nó`, para o conteúdo se adaptar ao modo recolhido (marca compacta, avatar sem nome).
- A ordem do DOM do `Layout` é skip link, `AppBar`, sidebar, `main`, rodapé (posicionados por CSS grid), para o botão de menu vir antes da sidebar no foco.
- Tooltip renderiza a bolha em portal com posição fixa, por isso funciona dentro de containers com scroll; item de menu recolhido usa `Tooltip` com `describe={false}`.
- `Modal`, `ConfirmModal`, `Drawer`, `Popover`, `Menu`, a lista do `Combobox`, o calendário do `DatePicker`, `Tooltip`, o `Loading` com `overlay` e o `ToastProvider` fazem portal para o `document.body` e aceitam `container` (elemento ou função que o devolve): quem resolve é o hook `usePortalContainer` (`src/hooks/usePortalContainer.ts`), num `useLayoutEffect` depois da montagem, nunca no servidor nem durante o render, porque uma função que procura um elemento da mesma árvore (`() => document.getElementById(...)`) só o encontra depois do commit; o hook resolve de novo quando a prop muda, e vazio ou `null` cai no `body`. Overlay novo com portal usa o mesmo util e a mesma prop, e entra no `describePortalContainerContract`. Os overlays são `position: fixed` com coordenadas da janela: um ancestral do contêiner com `transform`, `filter` ou `contain` vira o bloco de contenção e desloca o overlay, e um que cria contexto de empilhamento prende o `z-index` dele, ressalvas documentadas e não bugs.
- Dentro de um componente, estilo de layout com CSS explícito no `.module.css` (`display: flex`); `Flex`, `Grid` e `Container` servem para compor páginas.

## Contrato de componente (especificação para a passada por componente)

Especificação, não descrição: os componentes atuais ainda não cumprem tudo. Cada componente passa por ela uma vez, começando por `Button`, `Modal`, `Popover`, `Icon`, `Link` e `Tooltip`; um componente só conta como pronto quando cumpre todos os itens.

**Customização**
- A raiz aceita `className` e `style` e os espalha por último, com `mergeProps(own, user)` de `@utils/mergeProps.ts`: classes unidas (a de quem usa por último), `style` mesclado (quem usa vence), handlers dos dois (quem usa primeiro; o da lib não roda após `preventDefault`) e `data-slot` da lib preservado. A classe de quem usa vence a da lib sem `!important`.
- Cada parte relevante recebe `data-slot="<componente>-<parte>"` pelo helper `slot('modal', 'panel')` (`modal-panel`, `sidebar-item`). Quem estiliza de fora usa `data-slot` e `data-state`, nunca o nome da classe do CSS Module.
- Seletores internos que dependem de contexto usam `:where()` para manter a especificidade em zero e deixar a customização ganhar.
- Variantes e estados por atributo (`data-variant`, `data-size`, `data-state`), além das classes.
- Reset próprio em cada componente (botão, lista, link): nenhum componente depende de um reset global.
- `Grid`, `Flex`, `Container` e `Card` aceitam `as` entre as `structureTags` de `@utils/structureTag.ts` (`div` por padrão, `section`, `article`, `aside`, `nav`, `header`, `footer`, `main`, `ul`, `ol` e `li`) e escrevem `<Tag {...mergeProps(own, props)}>`. O tipo da raiz é `HTMLAttributes<HTMLElement>`, `ul` e `ol` levam `role="list"` (`roleOf`; o `role` de quem usa vence, porque o Safari tira a semântica de lista de quem tem `list-style: none`) e o CSS da raiz zera `list-style`, margem e padding. Link e botão nunca entram em `as`: são componentes próprios (`ButtonLink`, `CardLink`, `CardButton`). Uma tag nova entra na lista com o teste de `structureTag` e o spec `structureTags` de navegador.
- `CardButton` e `CardLink` são o `Card` clicável com o elemento certo, no molde do `ButtonLink` e do `Button`: a classe é `classNames(cardStyles.card, styles.tile)` (o `CardLink` ainda soma a própria `.link`), então a superfície (variante, padding, raio, sombra, lift) é a do `Card` e os ganchos continuam `--enchase-card-*`, com o `data-slot` próprio (`card-button`, `card-link`). A superfície sai de `useCardSurface` (`Card/surface.ts`); o `Card` e os dois tiles não repetem a conta. O `.tile` zera o que o `<button>` e o `<a>` trazem (fonte, cor, decoração, borda da variante `elevated`) e tem o anel de foco, as camadas de hover e de pressionado e o `disabled`; o pressionado vem depois do hover no CSS porque as duas regras empatam em especificidade e a última vence. O spec `Card/tile.spec.tsx` compara a superfície com a de um `Card` em cada variante e em cada estilo, então uma variante nova do `Card` que o tile não acompanhe aparece lá. O `type` padrão do botão é `button`; o `CardLink` não desenha ícone, só leva o texto de `labels.opensInNewTab`.
- `AccordionItem.title` e `TabsItem.label` são `ReactNode`. O conteúdo fica dentro de um `<button>`, então só cabem elementos de texto, e o texto de tudo o que está dentro é o nome do botão e do painel.

**Navegadores e o CSS publicado**
- O campo `browserslist` do `package.json` (Chrome e Edge 120, Firefox 129, Safari e iOS 17.5) é a política de suporte e a fonte única do piso: o `vite.lib.config.ts` o converte em `build.cssTarget` e os dois README o listam. O piso duro é o `inert` (Chrome 102, Safari 15.5, Firefox 112). O CSS publicado ainda passa pelo pipeline de quem usa, e o padrão do Vite tem alvo mais antigo (Chrome e Edge 111, Firefox 114, Safari e iOS 16.4): tudo o que o `lightningcss` dele consegue reescrever, ele reescreve. Por isso o `checkPackage.mjs` confere o `dist-lib/styles.css` e o `styles.layer.css` duas vezes, como publicados e depois do build padrão do Vite (`scripts/consumerCss.mjs`), e o `rtlDist.spec.tsx` repete no navegador os mesmos casos com os dois CSS. O CSS que os testes de navegador carregam do fonte não prova o que vai para o pacote, nem o que chega ao app.
- A leitura de `process.env.NODE_ENV` do `ColorModeProvider` fica dentro de um `try`, junto do código só de desenvolvimento (o aviso de contraste e de movimento do tema): em ESM nativo, sem bundler, `process` não existe e a leitura não pode derrubar a árvore. A forma `typeof process !== 'undefined' && ...` perde a remoção do aviso no bundle de produção, e o `testBundleSize.mjs` confere que ele não leva as mensagens do aviso.

**Camadas de CSS**
- O CSS-fonte dos componentes não usa camada. O build gera `enchase/styles.css` (normal), `enchase/styles.layer.css` (o mesmo CSS dentro de `@layer enchase`, com a ordem `enchase-theme, enchase-base, enchase`) e `enchase/theme.css` (tema padrão claro e escuro estático). Na variante em camada, qualquer CSS do usuário sem camada vence em qualquer ordem de carregamento; na normal, o layout vence por `:where()` e as cores só vencem se o CSS do usuário vier depois. O reset global do pacote fica em `@layer enchase-base`. O bloco da densidade `compact` não mora no CSS dos componentes: vai com o tema (`themeCss` e `theme.css`), dentro da mesma camada dele.

**Direção (RTL)**
- Só propriedades lógicas (`margin-inline-start`, `inset-inline-end`, `padding-block`, `text-align: start`, `border-start-start-radius`). Exceções (centralização com `translate`, `transform-origin`) documentadas no CSS do componente.
- Deslocamentos de movimento usam `start` e `end`, não `left` e `right`. O sentido vem de `dir` do `UIProvider`.
- Ícones direcionais (setas, chevrons) espelham em RTL por atributo, não por cópia.
- O que espelha em RTL lê o atributo `dir` com um seletor de atributo: `[dir='rtl'] .x`, e `:where([dir='rtl'] .x)` onde a especificidade tem de ser zero. Nunca `:dir(rtl)`: o `lightningcss` de quem usa (o padrão do Vite tem alvo Chrome e Edge 111, sem `:dir()`) o reescreve como lista de `:lang()`, que segue a língua da página e não a direção dela, e aí um documento `dir="rtl"` com `lang="pt-BR"` não espelha, e um documento LTR em árabe espelha. Nenhum pipeline reescreve um seletor de atributo. O limite é conhecido: uma ilha `dir="ltr"` dentro de um documento RTL não desespelha, e `dir="auto"` não conta como RTL. O `checkPackage.mjs` falha se o CSS publicado, ou o que sai do build padrão do Vite, tiver `:dir(` ou `:lang(`, ou perder um dos `[dir=rtl]` do fonte.

**Movimento**
- Só `transform` e `opacity`; nunca `width`, `height`, `margin`, `top`, `left` nem `transition: all`. A barra do `Progress` cresce por `transform: scaleX`, e o anel dele anima `stroke-dasharray`, que só repinta o SVG e não mexe no layout. Única exceção de layout: o recolher da `Sidebar` permanente anima `inline-size` (e a coluna do conteúdo acompanha), porque o custo medido é de cerca de 1,5 ms de layout por quadro e um teste mantém o limite de um quadro; não crie outra exceção sem medir.
- Uma curva e durações por token, nunca valor solto no componente: `--enchase-motion-duration-fast|base|slow` (150, 250, 300 ms), `--enchase-motion-ease-out` (`cubic-bezier(0.2, 0, 0, 1)`, a única curva de entrada e saída) e `--enchase-motion-ease-in-out` (`cubic-bezier(0.4, 0, 0.2, 1)`, só para o que já está na tela e se move), mais `--enchase-motion-distance-xs|sm|md` (2, 12 e 32 px: `lift`, `pop` e `slide`). Entrada com `ease-out`; saída mais curta que a entrada.
- Presença (montar e desmontar com saída animada): `usePresence(open, { exitMs })` de `@hooks/usePresence.ts` devolve `{ mounted, state, ref }`, com `state` em `entering | open | exiting | closed`. O CSS anima por `data-state`; o hook mantém o elemento montado até o `transitionend` ou `animationend` do próprio elemento (ou `exitMs`, padrão 300 ms) e aceita reabrir no meio da saída. Não usa `window` na renderização.
- Hover só dentro de `@media (hover: hover) and (pointer: fine)` escrito por extenso (custom media não entrou: precisaria do transformador Lightning CSS em todas as configs); o toque ganha feedback por `:active`. O teste `hoverGating` tem uma lista dos componentes que ainda têm `:hover` fora da media query: nenhum entra nela, e quem for corrigido sai dela.
- Pressionado e foco vêm depois do hover no CSS, com o mesmo seletor do hover (inclusive o `:not(:disabled)`): com o mouse pressionado `:hover` e `:active` casam juntos, e entre regras de mesma especificidade vence a última. O `pressedOverHover.test.ts` confere a ordem em todos os componentes e o `stateTokens.spec` mede a camada `::after` com o mouse pressionado e com o teclado focado (a camada pressionada vale `--enchase-state-pressed`, não a de hover).
- `prefers-reduced-motion`: movimento espacial some e o fade continua; nada depende de movimento para ser entendido.
- Interrompível: reverter no meio do caminho parte do estado atual.
- Mola: use os tokens `--enchase-motion-spring-gentle|snappy|bouncy` (função `spring()` gera a curva `linear()`), só em entradas ocasionais (`Modal`, `toast`, `Popover`, `Tooltip`); nada que o usuário vê dezenas de vezes por dia. Tooltip: o segundo tooltip aberto em até 300 ms entra sem animação.
- Posicionamento flutuante: use `src/positioning/` (`computePosition`, `autoUpdate`); nunca recalcule posição à mão em componente novo.
- Arrastar exige alternativa por clique ou teclado e anúncio em `aria-live` (WCAG 2.5.7).

**Tokens para presets**
- Altura de controle (`--enchase-control-height-sm|md|lg`: 2, 2,5 e 3 rem), raio de controle (`--enchase-radius-control`, 0,5 rem), raio de botão (`--enchase-radius-button`), sombra (`--enchase-shadow-*`) e duração (`--enchase-motion-duration-*`) vêm de variáveis do tema, para um preset trocar a pele sem mexer na estrutura. Sem valor fixo desses cinco dentro do CSS do componente. Os presets de forma (`shape: 'pill' | 'soft' | 'square'` no `createTheme`) trocam só os raios, em `src/styles/theme/shape.ts`.
- O anel de foco (`--enchase-focus-width|offset|offset-inset|offset-selector`: 2, 2, -2 e 3 px) e a largura de borda (`--enchase-border-width` e `--enchase-border-width-strong`: 1 e 2 px) também vêm de variáveis do tema. A cor do anel é `--enchase-focus-color`, opcional: o componente lê `var(--enchase-focus-color, var(--enchase-color-primary))`, para o anel continuar seguindo o `primary` de um trecho da página. O componente lê cada token com o padrão dele como fallback (`var(--enchase-focus-width, 2px)`), para o anel e a borda sobreviverem a um tema escrito antes do token; o teste `focusAndBorder` confere que o fallback é igual ao padrão de `baseTokens` e lista as únicas larguras fixas (glifos desenhados com borda e o spinner).
- As camadas de estado (`--enchase-state-hover|pressed|row-hover|disabled-container|disabled-content`: 0,08, 0,1, 0,06, 0,12 e 0,38) e o halo dos controles de seleção (`--enchase-halo-size`, 10 px, e `--enchase-halo-size-switch`, 0,5 rem) também vêm de variáveis do tema, lidas com o padrão como fallback. O teste `stateTokens` confere o fallback, que cada seletor (`:hover`, `:active`, `:disabled`) usa o token do seu estado e que só a translucidez da `Navbar` e da `AppBar` (80%) ainda escreve uma porcentagem.
- A área de toque (`--enchase-hit-size`, 40 px, e `--enchase-hit-size-lg`, 44 px, para os botões que abrem, fecham ou recolhem uma navegação) também vem de variável do tema. O componente lê `max(24px, var(--enchase-hit-size, 40px))`: o piso de 24 px (WCAG 2.5.8) fica fixo dentro da expressão, e o fallback é o padrão do token. O teste `hitSizes` confere o piso, o fallback e lista os únicos tamanhos de 40 px que ainda são fixos (avatar do `SidebarUser` e spinner do `Loading`).
- Ganchos do componente (`--enchase-<data-slot>-<propriedade>[-<variante>]`: o nome do `data-slot` da parte mais a propriedade, como `--enchase-switch-thumb-size` para o tamanho de `data-slot="switch-thumb"`, ou `--enchase-button-padding-inline-md` para o tamanho `md`; um glifo sem slot leva o slot da parte que o contém, como `--enchase-checkbox-box-check-width`): o tema não os declara, o componente lê `var(--enchase-switch-thumb-size, 1.5rem)` e o fallback é o único lugar onde o padrão mora, igual em todo uso do gancho. Medida que depende de outra se deriva por `calc()` (o traço do checkbox, o ponto do radio, o curso da chave), nunca por um segundo número fixo, e um valor intermediário vai numa variável privada sem o prefixo `enchase` (`--switch-travel`, `--radio-dot-size`). Quando o padrão já é um token de escala, o gancho cai nele (`var(--enchase-button-padding-inline-md, var(--enchase-space-lg))`), para o componente continuar seguindo uma sobrescrita da escala. O teste `selectorGeometry` confere que nenhuma medida do checkbox, do radio e da chave fica escrita fora de um gancho, o `buttonGeometry` confere o mesmo para o padding, a fonte, o peso e o espaço do `Button`, o `fieldGeometry` para a largura, o padding e a fonte dos quatro campos (que dividem os ganchos `--enchase-input-*`), e os `.spec` de mesmo nome conferem no navegador que cada gancho muda o computed. Medida que depende de outra se deriva, nunca se copia: o rótulo flutuante sobe metade de `--enchase-input-height`, o rótulo acompanha o padding do texto, e o espaço que o campo reserva para os botões de dentro sai de `--enchase-hit-size`. Ficam fixos, e o teste os lista, o entalhe do rótulo flutuante, o espaço da seta do `Select` e o deslocamento do rótulo da `Textarea`.
- A tipografia (`font-size`, `font-weight`, `line-height`, `letter-spacing`, `text-underline-offset`) e os cantos (`border-radius`) de cada parte vêm de ganchos `--enchase-<data-slot>-<propriedade>` com o token da escala como fallback (`var(--enchase-alert-radius, var(--enchase-radius-md))`). A entrelinha e o espaçamento entre letras têm escala própria no tema (`--enchase-line-height-none|tight|snug|normal|relaxed` e `--enchase-letter-spacing-tight|control`), lida com o padrão como último fallback (`var(--enchase-line-height-normal, 1.5)`). O teste `typographyShape` confere que nenhuma dessas propriedades fica escrita fora de um gancho, que o fallback é o token da escala ou o padrão do token de entrelinha, que o nome do gancho é o `data-slot` da parte mais a propriedade e que o campo e o contorno dele dividem o gancho do canto; ele lista o que fica fixo (a tipografia do rótulo flutuante dos campos, que o entalhe do contorno acompanha); a entrelinha da migalha de baixa prioridade segue o gancho de altura mínima do link. A lista de ganchos de todos os componentes é gerada do CSS na seção "Ganchos de CSS" do `API.md` (`npm run docs:api`), e uma mudança de padrão aparece como diferença nela.
- O espaço (`padding`, `margin`, `gap`), o tamanho (`min-height`, `max-width`, `width`...), a cor (`background`, `color`, `border-color`, por variante) e a sombra (`shadow`) de todos os componentes (os contêineres, as barras e a navegação, os controles, os campos, o toast, o popover, o tooltip, o `Loading` e o `Skeleton`) também vêm de ganchos, com o token da escala (`--enchase-space-*`), o papel de cor (`--enchase-color-*`) ou a sombra do tema (`--enchase-shadow-*`) como fallback. O teste `boxHooks` confere que nenhuma dessas propriedades fica escrita fora de um gancho em nenhum componente (ele lista o que fica fixo: o entalhe do rótulo flutuante, a ocultação visual, valores derivados, relativos à janela ou feitos de `min()`/`calc()`), que o fallback é um token que existe, que cada gancho tem o mesmo fallback em todo uso (menos o par `vh`/`dvh` do popover) e que o nome segue o `data-slot` (as partes sem slot, como `pagination-control`, `select-option` e `select-picker`, ficam numa lista no teste). Os quatro campos dividem os ganchos de cor, de vão e de estado com o nome `--enchase-input-*` (`--enchase-input-outline-border-color-focus`, `--enchase-input-label-color-error`, `--enchase-input-helper-color`); o que é só de um campo leva o nome dele (`--enchase-input-toggle-color`, `--enchase-number-input-stepper-color`, `--enchase-select-option-background-checked`). Os mistos de cor de estado (`color-mix` do hover, do pressionado e do desabilitado) não são ganchos: seguem os tokens `--enchase-state-*`. Os vãos que o `Footer` e o `ConfirmModal` passavam ao `Flex` em `gap="..."` agora saem de classes com ganchos (`--enchase-footer-gap`, `--enchase-footer-links-gap`, `--enchase-modal-footer-gap`). A sublinha da aba selecionada e o indicador deslizante dividem o gancho `--enchase-tabs-indicator-color`, e as células do cabeçalho, do corpo e do cabeçalho de linha da tabela dividem os ganchos `--enchase-table-cell-*`. Um gancho de cor que o estilo deriva de outro papel de cor se declara dentro do seletor do modo, não só no `:root` (um alias resolve onde é declarado: no `:root` ele acompanha o modo do documento, mas não o de uma ilha `data-theme` aninhada). As barras translúcidas derivam o fundo do gancho sólido e do alpha (`--enchase-navbar-background-solid` e `--enchase-navbar-background-alpha`, e `--enchase-app-bar-*` na `AppBar`); o `--enchase-navbar-background` e o `--enchase-app-bar-background`, documentados desde a 0.7.0, continuam sendo o fundo translúcido inteiro e vencem a derivação, e o fundo sólido também é o que a barra usa de volta quando o sistema pede menos transparência. O indicador deslizante da `Sidebar` pinta com `--enchase-sidebar-indicator-background`, que cai em `--enchase-sidebar-item-control-background-current` (o item atual), e a largura dele segue `--enchase-sidebar-nav-padding-inline`.
- Variável que só aponta para outra (um alias) é resolvida no `:root`, e uma sobrescrita só num trecho da página não a alcança. Para um papel que deve seguir a cascata, o componente lê um override opcional com fallback (`var(--enchase-x, <padrão>)`) em vez de um alias emitido pelo tema.
- A densidade `compact` é dado e CSS, sem API (nada em `lib/`, nada no `createTheme`, no `ThemeInput` nem no `ThemeSet`): o dado puro `densities.compact` (`tokens` e `hooks`, em `src/styles/tokens/density.ts`, sem imports e reexportado por `tokens/index.ts`) e o `densityRules` de `src/styles/css/declarations.ts`, que o `themeCss` escreve logo depois do `layoutVariablesRule`, dentro da mesma `@layer` quando há `cssLayer`. Por isso o bloco sai também no `theme.css`, uma vez, e em nenhum outro CSS do pacote: o `checkPackage.mjs` falha se o `styles.css` ou o `styles.layer.css` lerem `data-density` ou se o `theme.css` tiver o bloco fora das duas regras exatas, e o `testBundleSize.mjs`, o `testConsumer.mjs` e o `testNext.mjs` conferem o bloco no orçamento, no pacote empacotado e no HTML de servidor. São duas camadas de força: os tokens (`--enchase-hit-size`, `--enchase-control-height-sm|md|lg` e `--enchase-space-sm` a `3xl`) em `:root[data-density='compact']` (0,2,0, vencem o `:root` do tema em qualquer ordem de carga) e os ganchos (as alturas que o `enchase` escreve no componente e nenhum token alcança: campo, `textarea`, aba, acordeão, opção do `Select`, `Badge`, item e cabeçalho da `Sidebar`, barra da `Navbar` e do `Layout`) em `:where(:root[data-density='compact'])` (0,0,0, perdem para o gancho de um estilo, do app ou do próprio componente). Só tokens deixariam o `enchase` com botões de 32px em campos de 56px, e tudo na força dos tokens faria o `shadcn`, que declara esses ganchos, crescer. Por isso o `shadcn` fica meio compact: segue os tokens e, dos ganchos, só os que declara como alias de um token do bloco (`--enchase-input-height` e `--enchase-tabs-tab-min-height`, alias de `--enchase-control-height-md`).
- O `data-density` só vale no `<html>`: todo seletor do bloco começa com `:root`, então num `div` ou no `<body>` o atributo não faz nada, e não há ilhas (os overlays saem no `<body>`, que só a raiz alcança). Ele aceita `compact`: sem o atributo, com `default` ou com qualquer outro valor vale o padrão, não existe `spacious` e não há volta ao padrão dentro de uma árvore compact. O bloco declara só variáveis `--enchase-*` dos grupos `space`, `control` e `hit`, nunca tipografia (o rótulo flutuante e o entalhe do contorno dependem dela), raio, foco, borda, estado nem movimento. Os valores são absolutos e ficam no nível do de cada estilo embutido (os tokens) ou do fallback do componente (os ganchos) ou abaixo dele, para o compact não fazer nada crescer; `--enchase-space-md` é o dobro de `--enchase-space-sm` (o rótulo flutuante acompanha o entalhe) e `--enchase-hit-size-lg` fica em 44px, fora do bloco. O alvo de toque vai a 32px em qualquer ponteiro (o compact não é para interface pensada para o dedo) e o piso de 24px continua valendo (`max(24px, var(--enchase-hit-size, ...))`; o polegar do `Slider` é o único alvo abaixo dele, como já era). Os valores são calibrados para os estilos embutidos: um estilo próprio de `defineStyle` recebe o mesmo bloco e não pode declarar o compact dele, e num estilo cujo padrão já é mais denso que o do `enchase` uma peça pode não compactar ou até crescer (o piso de 24px continua valendo).
- Quem usa vence o bloco assim: um gancho no `:root` ou no próprio componente vence nos dois builds; um token no `:root` perde para o bloco no build sem camada (0,2,0 contra 0,1,0, antes ou depois do tema) e vence no build em camada (`cssLayer`), que é a recomendação; `html:root[data-density='compact']` (0,2,1) vence em qualquer ordem e `:root[data-density='compact']` (0,2,0) só vence se vier depois do tema. Os guardas: `src/tests/styles/density.test.ts` (jsdom: o texto do bloco, o seletor, as duas camadas, o que o bloco declara e os limites acima, em todo tema, com e sem camada), `src/tests-browser/styles/density.spec.tsx` (o tamanho de cada peça nos dois estilos, o piso de 24px, o rótulo flutuante e o entalhe, o padrão idêntico sem o atributo e a troca em tempo de execução), `densityIsland.spec.tsx` (o atributo fora do `<html>` não muda nada) e `densityLayer.spec.tsx` (a precedência contra a camada e contra o CSS do app). A página `System/Density` do Storybook tem a tabela dos tokens e dos ganchos (`src/docs/stories/system/Density/defaultData.ts`), que o `src/tests/docs/stories/system/Density/defaultData.test.ts` confere contra `densities`, contra o `shadcn` e contra o CSS dos componentes, então mudar um valor é mudar `density.ts` e essa tabela, e a lista do que o `shadcn` segue sai dela. O item `density` da barra do Storybook liga o atributo no `<html>` (`DensityAttribute`, no `withProviders`) e o tira ao desmontar, para ele não ficar preso na história seguinte.

O guia completo, em português, é o `README.pt-BR.md`, e uma mudança de comportamento público entra nele; mudou o início rápido, os navegadores ou o que a biblioteca garante, entra nos dois. Os blocos `tsx` do `README.md` são módulos completos, e o `npm run test:consumer` os compila contra o pacote empacotado (`strict`, `exactOptionalPropertyTypes`), com um `App` vazio no lugar do `./App.tsx` do bloco do Vite.

## Animação (motor próprio, CSS primeiro)

- Sem biblioteca de animação: o movimento é CSS (transições, `@starting-style`, `@keyframes` só para loops, `linear()` para mola) mais o hook `usePresence` para montar e desmontar com saída. Nada de importar `motion`.
- Os tokens (`--enchase-motion-duration-*`, `-ease-*`, `-distance-*`, `-spring-*`) vêm do tema (`createTheme({ motion })`, validado: duração acima de 300 ms em UI gera aviso). Nunca valor solto no CSS do componente.
- Cada componente com animação lê as próprias variáveis `--enchase-<componente>-duration|exit-duration|distance|dx|dy|scale|ease` (tabela no `README.pt-BR.md`); o usuário muda por tema, pela prop `animation` ou pelo CSS dele.
- Os dados das receitas (`fade`, `pop`, `slide`, `press`, `lift`, `spin`, `shimmer`) ficam em `src/motion/`; `resolveCssMotion` e `resolveLoopMotion` os transformam em variáveis e atributos (`data-motion`).
- Todo componente animado aceita `animation?: MotionOverride` (`false` desliga; `{ recipe, from, tuning }` ajusta) e respeita o `UIProvider` (`mode`, `preset`, `recipes`). `mode='never'` desliga tudo.
- Saída animada com `usePresence`; ele lê a duração real do estilo calculado, então nunca `setTimeout` para esperar a animação.
- `prefers-reduced-motion`: o deslocamento e a escala viram `none` e a opacidade continua (fade curto); loops (`data-motion='on'`) viram pulso de opacidade. O CSS de cada componente decide isso; não há regra global que zere as transições.
- Gesto e velocidade (arrastar, inércia, rubber-band) ainda não existem: ficam para a camada 2 e entram só quando um componente pedir.

## Nomenclatura e tipagem

- Inglês, camelCase, sem abreviações.
- Zero `any`. Use `import type` para tipos.
- Toda propriedade opcional de um tipo leva `| undefined` (`prop?: T | undefined`, e uma função entre parênteses: `onClose?: (() => void) | undefined`), para quem usa `exactOptionalPropertyTypes` poder passar um valor que pode ser `undefined`, como `error={errors.email?.message}`. O `optionalProps.test.ts` varre o `src/` e reprova a que falta, o `explicitUndefined.test.tsx` confere que passar `undefined` rende o mesmo que omitir (por isso o componente lê a prop com padrão de desestruturação ou com `!== undefined`, nunca por presença da chave), o `testConsumer.mjs` compila com a flag ligada, e o gerador do `API.md` esconde o `| undefined` da tabela. `Partial<...>` aninhado (`labels`, `motion`, `breakpoints`) não entra: nele um `undefined` explícito sobrescreve o padrão.

## Estrutura e limites

- Arquivos com mais de ~200 linhas devem ter lógica extraída para hooks (Single Responsibility Principle).
- Faça somente o solicitado — escopo contido.

## Imutabilidade e performance

- Prefira `.map`/`.filter`/`.reduce`/spread; evite loops (`for`/`while`) e mutação direta de estado.
- Early return em vez de `if/else` aninhado.
- `Promise.all` para chamadas assíncronas independentes — nunca `await` sequencial sem necessidade.
- Substitua `switch/case` ou `if/else` longos por objetos literais ou `Map`.

## Acessibilidade (WCAG 2.2 AA) e segurança

- HTML semântico (`<header>`, `<nav>`, `<main>`, `<footer>`) em vez de `<div>` genéricas; cada `nav` com `aria-label`, sem `nav` aninhado.
- Todo texto lido por tecnologia assistiva (`aria-label`, mensagens, títulos padrão) vem de `useUIConfig().labels`, nunca fixo no componente, para ser configurável no `UIProvider`.
- Ids de associação (`label`/`aria-describedby`/`aria-labelledby`) gerados com `useId`, nunca strings fixas nem `props.id` indefinido.
- Estado exposto por atributo, não só por cor ou CSS: `aria-expanded`, `aria-invalid`, `aria-current`, `checked` nativo. Estilize via seletores de estado (`:checked`, `:disabled`, `:focus-visible`), não por prop espelhada.
- Foco sempre visível (`:focus-visible` com contraste ≥ 3:1), alvos interativos ≥ 24×24px e navegação completa por teclado.
- Diálogos e drawers usam `useModalBehavior` (focus trap, `inert` no restante da página, trava de scroll com restauração, ESC e devolução do foco). O `Drawer` público, o `Sidebar` modal e o drawer do `Navbar` compartilham a `DrawerLayer` (`src/components/common/Drawer/DrawerLayer.tsx`): ela monta a raiz, o overlay e o painel com `useOverlayStack`, `useModalBehavior`, `role="dialog"`, `aria-modal` e o clique no overlay, e cada um passa os próprios `data-slot`, classes e estilos, então o CSS e os ganchos do `Sidebar` e do `Navbar` ficam onde estavam. O `Drawer` faz portal (`usePortalContainer`), tem `side` (`start` ou `end`, que espelha em RTL pelo `dx` da receita `slide`) e desliza o próprio tamanho (`100%`), não uma distância fixa. Conteúdo dinâmico usa regiões `aria-live`; erros usam `role="alert"` (o toast usa dois anunciadores ocultos, veja abaixo).
- O que recebe Tab tem uma definição só, `tabbablesIn` de `@utils/tabbable.ts`, usada pelo `useFocusTrap` e pelo `Popover`: o seletor inclui `contenteditable`, `summary`, `iframe` e mídia com `controls`, deixa de fora `input type="hidden"`, `tabindex` negativo e `fieldset disabled`, e só lista o que o navegador renderiza (`checkVisibility`, ou o estilo calculado onde ele não existe, como no jsdom), na ordem do documento (o `querySelectorAll` do jsdom agrupa por seletor). O trap anda por `focusInOrder`, que passa para o próximo candidato quando um não aceita foco: nunca fica preso. Não escreva outro seletor de focáveis. O `focusTrap.spec` confere isso em navegador real, porque o jsdom aceita `focus()` em um elemento escondido.
- Navegação por teclado em listas (setas, Home, End e digitação) tem uma definição só, o hook interno `useListNavigation` de `@hooks/useListNavigation.ts`: recebe os itens (`disabled`, `text`), `orientation` (`vertical`, o padrão, `horizontal` ou `both`; no horizontal, ArrowLeft e ArrowRight se invertem em RTL, lido do estilo calculado de `event.currentTarget`), `loop` (padrão `true`) e `typeahead`, e devolve uma função que recebe o evento de teclado e o índice atual e responde com o índice de destino, ou `undefined` quando a tecla não é dele (com Alt, Ctrl ou Meta, ou com Shift em Home, End e setas). Itens desabilitados são pulados, e a digitação junta as letras por 500 ms, procura a partir do item seguinte (a mesma letra repetida cicla entre os que começam com ela) e compara com o `text` do item. O hook não move o foco nem mexe em `tabindex`: quem usa aplica o índice e mantém o `tabindex` móvel (um item habilitado com `0`, os demais com `-1`).
- O `Checkbox` com `indeterminate` liga a propriedade `indeterminate` do `<input>` nativo (não há atributo HTML para ela), num `useLayoutEffect` que acompanha a prop, e o visual vem da pseudo-classe `:indeterminate`, então o leitor de tela e o desenho leem o mesmo estado e uma caixa mista renderizada no servidor só aparece mista depois da hidratação. O navegador limpa `indeterminate` ao clicar, então um `onClick` do componente (que roda depois do `onClick` de quem usa, e não roda se ele der `preventDefault`) a repõe numa microtarefa com o valor da prop mais recente, depois de o React processar o `onChange`: a prop manda, o clique nunca a limpa sozinho, e quem usa a limpa no `onChange`. A caixa mista tem o preenchimento da marcada (os mesmos ganchos `-checked`), um traço no lugar do visto (`--enchase-checkbox-box-size` e `--enchase-checkbox-box-check-width`, sem gancho novo) e não ganha a borda de erro, como a marcada.
- O `Menu` é o `Popover` com `role="menu"` (a prop `role` aceita `dialog`, `listbox`, `tree`, `grid` e `menu`). Com `menu`, o corpo que rola não recebe `tabindex` (os itens têm o foco, e o axe recusa um filho focável genérico dentro de `role="menu"`), Tab fecha o menu e leva o foco ao próximo elemento depois do gatilho, Shift+Tab fecha e devolve o foco ao gatilho, e o `PopoverControl` (`close`, que fecha e devolve o foco ao gatilho, e `contentRef`) chega ao conteúdo por `usePopoverControl`. Os itens são `button` com `role="menuitem"`, `aria-disabled` (nunca `disabled`, e fora da navegação por setas) e `tabindex` móvel; o `Menu` escuta o `keydown` no conteúdo e delega ao `useListNavigation`. O gatilho é o `children` clonado: ArrowDown abre no primeiro item, ArrowUp no último, e clique, Enter e Space abrem com o foco no primeiro; um `defaultOpen` não rouba o foco. Fora do escopo: submenus, itens com checkbox ou rádio e itens com `href`.
- O `Combobox` segue o padrão combobox do ARIA 1.2 com autocompletar de lista: o foco do DOM nunca sai do `input` (`role="combobox"`, `aria-expanded`, `aria-controls` e `aria-activedescendant` com o `id` da opção ativa) e a lista é um `role="listbox"` em portal, o `ListboxPopup` de `Combobox/subcomponentes`, e não um `Popover`: o `Popover` leva o foco para dentro e tem semântica de diálogo. A lista reaproveita os ganchos do `Popover` (`usePresence`, `useOverlayStack`, `usePopoverTree`, `usePortalContainer`, `computePosition` e `autoUpdate`), abre embaixo do campo com a largura dele no mínimo, vira para cima quando falta espaço e fecha com Esc (só a do topo, então um Esc dentro de um `Modal` fecha primeiro a lista), com clique fora e quando o foco sai do campo; o `mousedown` na lista é cancelado para o foco ficar no campo, e as opções são `div role="option"` sem `tabindex`. A opção ativa acompanha o ponteiro por `pointermove`, não por `mousemove`: o dedo (`pointerType` `touch`) não ativa nada, porque deixaria uma opção marcada depois de um toque ou de uma rolagem, e um movimento confiável (`isTrusted`) com as mesmas coordenadas do anterior é descartado, porque o WebKit dispara um quando a lista rola sob o mouse parado e a opção ativa voltaria para a que está sob o ponteiro enquanto as setas andam (os eventos sintéticos das ferramentas de teste valem sempre). As setas, Home, End e a digitação são do `useListNavigation`; o estado (valor controlável, texto digitado, opção ativa, aberto e a lista filtrada) é do `useCombobox`, e o filtro padrão (`filterOptions.ts`) ignora maiúsculas e acentos. O valor é sempre uma lista de `value` de opções (`string | null` no modo simples, `string[]` com `multiple`), nunca o texto digitado: ao sair do campo o texto digitado é descartado e volta o rótulo da escolha, e esvaziar o texto e sair limpa a escolha no modo simples. O rótulo de uma opção escolhida fica numa memória do hook (lida depois das `options`), para um app que troca as `options` durante uma busca não esvaziar o campo nem as etiquetas. O `name` rende um `input type="hidden"` por valor, e o `input` visível não tem `name`. Sem resultado e carregando são linhas `role="option"` com `aria-disabled`, e uma região `role="status"` fora da lista anuncia as duas. Fora do escopo: criar uma opção a partir do texto digitado, agrupar opções e virtualizar a lista.
- O `DatePicker` é um `<input type="text">` comum (sem `role`) mais um botão que abre o calendário num `Popover` com `role="dialog"` (o `Popover` da biblioteca, e não uma cópia como o `ListboxPopup` do `Combobox`, porque aqui o foco precisa entrar no diálogo). O gatilho do `Popover` é o botão (`DatePickerToggle`), mas o `span` do gatilho cobre o controle inteiro (`position: absolute; inset: 0; pointer-events: none`, com o botão em `pointer-events: auto`): o diálogo se ancora ao campo (`bottom-start`, a 4 px dele) e não só ao botão, e um clique no campo cai fora do gatilho, o que fecha o calendário para quem vai digitar. O valor é sempre o texto ISO local `YYYY-MM-DD` (`string | null`; um texto que não é data vale como vazio), a conta de datas é toda em inteiros (`src/utils/calendarDate.ts`: o único `Date` é o de `todayDate`, chamado quando o calendário monta, e o calendário só monta no cliente, então o servidor nunca escreve um "hoje") e o formato vem do `locale` do `UIProvider` pelo `createDateFormat` (`src/utils/dateFormat.ts`: `Intl.DateTimeFormat` com `calendar: 'gregory'` e `timeZone: 'UTC'`, ordem e separadores pelo `formatToParts`, dígitos de outros sistemas de numeração e ano abaixo de 1000 escrito com quatro dígitos). A prop `locale` (uma tag BCP 47, em `string`) vale no lugar do `locale` do provider só para a tag que o `createDateFormat` e o `firstDayOfWeek` recebem (`props.locale || config.locale`, no `useDatePicker` e no `Calendar`, que a recebe pelo `DatePickerCalendar`; uma string vazia vale como ausente, porque quem a passa não quer sobrescrever): decide a ordem, os separadores e os dígitos do texto, os nomes dos meses e dos dias e o primeiro dia da semana, e o `firstDayOfWeek` continua vencendo. Não aceita o objeto `Locale`, porque `messages` e `dir` seguem o provider (quem quer tudo diferente envolve o campo num `UIProvider` próprio). A tag, a da prop e a do provider, passa por uma só função, `resolveLocale` (`src/utils/resolveLocale.ts`), que `createDateFormat`, `firstDayOfWeek` e `createNumberFormat` chamam uma vez cada: o `Intl.getCanonicalLocales` só serve para pegar o `RangeError` (uma tag malformada, como `en_US` ou a string vazia, vira `en`), e o `supportedLocalesOf` do construtor que vai ser usado, com `localeMatcher: 'lookup'` (o único que responde igual em todo motor), manda para `en` a tag que o ambiente não conhece (`xx`, ou um idioma sem dados de ICU, como tudo que não é inglês num Node com `small-icu`), sem lançar; sem isso o `Intl` usaria o locale padrão do ambiente e o servidor e o navegador escreveriam datas diferentes. Uma região que o ambiente não conhece num idioma que ele conhece (`en-XX`, `pt-XX`) fica, e o texto vem do idioma; a semana vem do `Intl.Locale` da tag, que dá segunda-feira para a região desconhecida. O `NumberInput` recebe a mesma prop, com o mesmo contrato (`props.locale || config.locale` no `useNumberField`, que passa a tag ao `createNumberFormat`: o separador decimal, o agrupamento, os dígitos e o lugar do símbolo da moeda, no que se mostra, no que se digita e no `aria-valuetext`, e o campo oculto do `name` continua com o número simples); outro componente que venha a formatar por `Intl` recebe a mesma prop com o mesmo contrato e passa pela mesma função. O texto digitado é um rascunho, como o do `NumberInput` (o `useDatePicker` usa a mesma troca durante o render: o valor ou o formato que muda refaz o texto): vale ao sair do campo e com Enter, que também fecha o calendário; um texto que não é data, ou que `min`, `max` ou `isDateDisabled` recusam, volta ao texto da data atual sem chamar `onValueChange`, e o texto vazio limpa. Ao abrir, o `Calendar` (interno, em `DatePicker/subcomponentes/Calendar`) leva o foco ao dia escolhido, ou a hoje, com `focus({ preventScroll: true })`, tanto por clique quanto por teclado, menos quando nasceu aberto (um `defaultOpen`, ou um `open` na primeira renderização, não rouba o foco da página; o hook marca "abriu depois da montagem" comparando o `shown` de cada render). O `Popover` só move o foco ao abrir por teclado, para o primeiro tabulável, e deixa onde está o foco que o conteúdo já pôs dentro de si. Escolher um dia, ou Esc, fecha e devolve o foco ao botão pelo `PopoverControl`. Rótulos novos e opcionais em `UILabels`: `openCalendar` (o botão), `chooseDate` (o nome do diálogo), `previousMonth` e `nextMonth`. A grade (`<table role="grid">` nomeada pelo título do mês, `td role="gridcell"` com `aria-selected`, `aria-current="date"` e `aria-disabled`, o título numa região `aria-live`, foco móvel, setas trocadas em RTL pelo estilo calculado e sempre seis semanas) segue o padrão de grade de datas do APG. Fora do escopo: faixa de datas, hora, várias datas e escolher o mês ou o ano por uma lista.
- O `Slider` é um único `div role="slider"` (um valor só: faixa com dois botões fica fora do escopo) com `aria-valuemin`, `aria-valuemax` e `aria-valuenow` sempre presentes e `aria-valuetext` só com `formatValue`. O valor mostrado é sempre o `snap` do armazenado (arredondado ao `step` a partir de `min`, preso ao último passo que cabe antes de `max` e sem resíduo de ponto flutuante), então um valor fora da faixa ou fora de um passo nunca chega ao DOM nem ao `onValueChange`, que só dispara quando o valor muda. O ponteiro captura na área de controle (`setPointerCapture`) e mede contra o `getBoundingClientRect` da trilha; a direção vem do estilo calculado (`getComputedStyle(...).direction`), que inverte a razão do ponteiro e as setas Left e Right, e a trilha usa só propriedades lógicas (`inset-inline-start`, `inline-size`). `touch-action: pan-y` deixa a rolagem vertical com o navegador, e `data-dragging` desliga as transições para o botão seguir o ponteiro sem atraso. Um toque só mexe no valor quando é um toque curto (aplicado ao soltar) ou quando passa de 6 px na horizontal sem andar mais na vertical, porque o gesto de rolar termina em `pointercancel` e não pode ter alterado nada; mouse e caneta mexem já no `pointerdown`. O foco vai ao botão por código depois de um `pointerdown` cancelado, o que faz o `:focus-visible` casar em todos os motores, então a raiz leva `data-pointer-focus` até a próxima tecla ou o `blur`, e o anel só aparece para o teclado.
- A `Table` não ordena os dados: a coluna com `sortable` ganha um `button` dentro do `th` (o rótulo num `span` e o `SortIndicator`, interno, um `svg` com dois triângulos e `data-direction`), o app guarda o `sort` (`{ key, direction }`) e ordena as `rows`, e o clique chama `onSortChange` com a direção seguinte: ascendente numa coluna que não está ordenada e a oposta na que está, sem estado de limpar (o APG faz o mesmo). `aria-sort` vai no `th` de qualquer coluna cuja chave seja a do `sort`, com ou sem botão, porque descreve a ordem das linhas, e só nessa. O botão cobre a célula inteira por um `::after` absoluto (o `th[data-sortable]` é `position: relative`), e o anel de foco é desenhado nesse `::after`, com deslocamento interno, porque o contêiner corta o que passa da borda; em colunas `end` o ícone vem antes do texto (`row-reverse`), para o texto ficar alinhado com os números. `stickyHeader` põe `position: sticky` nas células do cabeçalho e `isolation: isolate` no contêiner (o `z-index` do cabeçalho não vaza), mas só cola dentro de um contêiner com altura limitada (`style` ou `className` do app); por isso o `useOverflow` mede também a altura, e o contêiner que rola na vertical fica focável e com nome, como o que rola na horizontal. `loading` troca as linhas por linhas de `Skeleton` (a mesma quantidade, ou cinco se não há linhas) escondidas dos leitores de tela, põe `aria-busy` na `<table>` e mantém uma região `role="status"` visualmente oculta, criada quando `loading` não é `undefined` (uma região viva precisa existir antes de mudar), que fala o rótulo `loading`; o conteúdo de `empty` não aparece enquanto carrega.
- A seleção de linhas da `Table` é controlada e não tem estado próprio: `selectedKeys` (a lista de chaves, mesmo vazia, liga a coluna) e `onSelectedKeysChange`, que recebe sempre a lista inteira nova (`rowSelection` e `rowKeysOf`, puras, em `Table/rowSelection.ts`: a linha entra no fim ou sai, o "selecionar todos" acrescenta as que faltam sem repetir chave e, com todas selecionadas, tira só as chaves das linhas da tabela, então a seleção de outras páginas sobrevive). A chave é a de `getRowKey` ou, sem ele, o índice da linha, então a seleção só acompanha o registro numa tabela reordenada com `getRowKey`. A primeira coluna é um `th` (`data-slot="table-select-header"`) com o `Checkbox` de `labels.selectAllRows`, `checked` quando todas as linhas estão selecionadas e `indeterminate` quando só algumas (nada selecionado ou tabela sem linhas não é nenhum dos dois), desabilitado sem linhas e em `loading`, e um `td` (`table-select`) por linha, com o `Checkbox` de `labels.selectRow` ligado por `aria-labelledby` (o próprio id e o da primeira coluna `rowHeader`, que ganha `id`) para o nome ser "Selecionar linha #1042" e não o mesmo texto em toda caixa. Sem coluna `rowHeader`, o nome é o rótulo só. A linha selecionada leva `data-selected` e não leva `aria-selected`: é tabela, não grade. O `colSpan` de `empty` conta a coluna nova, e as linhas de `loading` ganham uma célula vazia para manter a largura. A coluna encolhe pelo conteúdo (`inline-size: 1%`), sem `padding-block` (a caixa já tem a área de toque do `--enchase-hit-size`) e o `Checkbox` vira bloco flexível centralizado por `[data-slot='checkbox']`. O fundo da linha selecionada é `--enchase-table-row-background-selected` (padrão `--enchase-color-surface-container-high`, que tem o contraste do texto garantido), e o `:hover` de uma linha selecionada põe a camada de hover por cima do fundo (`linear-gradient`), em vez de trocar o fundo.
- Uma região `aria-live` que fica fora do diálogo, como a região de notificações do toast, não pode ficar sob o `inert`: subárvore inerte não é anunciada e não recebe clique. O `ToastProvider` cria no render (atrás do `useIsClient`, então nada no servidor nem na hidratação) um `div` host com `data-slot="toast-host"` e `display: contents`, anexa o host ao `body`, ou ao `container`, em um `useLayoutEffect` (o cleanup o remove) e faz o portal da região para ele, junto de dois anunciadores `VisuallyHidden` persistentes (`role="status"` para success, info e warning, `role="alert"` para error) que existem antes de qualquer toast e leem o texto de cada notificação (o `useAnnouncer` limpa o texto e o repõe depois de 50 ms, para repetir um texto igual, e junta as mensagens de uma rajada, e só lê a mensagem, não o rótulo da ação); `update(id, patch)` troca o `toast` no lugar (mensagem, tipo, duração, ação, `dismissible`) e `promise` usa `update` quando a promise termina (o toast de carregamento é fixo, `duration` 0, e só ganha a duração padrão no resultado; se foi fechado antes, nada aparece); a duração nova reinicia a contagem e a barra de progresso (`key={duration}`); a pausa da contagem é da pilha inteira (o ponteiro ou o foco em qualquer ponto da região, tratados no `ToastProvider`, e cada item só recebe `paused`); `limit` mostra só as primeiras entradas que não estão fechando (as outras esperam, sem anúncio nem contagem, e `removeToast` de uma que espera a descarta); `position` (`top-end`, `top-start`, `bottom-end`, `bottom-start`) vira `data-position` na região, o CSS usa propriedades lógicas e o `slide` entra do lado do `start` ou do `end`; a região visual é só um `role="region"` nomeado, sem `aria-live`, e os itens não têm `role`; o `useInertSiblings` mantém fora do `inert` todo host marcado (`inertExemptSlot`) e a cadeia de ancestrais dele, e só torna inertes os irmãos dessa cadeia: um host dentro de um `container` do app continua alcançável sob um modal. O host existe porque um portal direto no `body` quebra a desmontagem do React quando algo esvazia o `body` antes, e o `ToastProvider` fica montado o tempo todo. Ele nasce no render, e não num efeito, para o portal montar no primeiro commit: com um commit a mais, o WebKit lê o padding do primeiro `select` antes do primeiro frame. O marcador é detalhe interno e não está em `lib/`: não é uma API para isentar uma região do usuário, o que pede uma camada comum de portais (`Modal`, `Tooltip`, `Popover`, toast e `Drawer`), ainda não desenhada.
- O `Tooltip` fecha com Esc por um `keydown` no `document` enquanto está aberto (WCAG 1.4.13), tenha ele sido aberto pelo foco ou só pelo ponteiro.
- O script inline do modo de cor monta cada valor com `scriptLiteral` (`JSON.stringify` com o `<` trocado por `\u003c`), para uma chave de armazenamento com `</script>` não fechar o script.
- Elementos decorativos (`svg` de ícone, spinner, skeleton) com `aria-hidden="true"`; spinner com texto alternativo oculto via `VisuallyHidden`.
- Paleta (`src/styles/tokens/`) nos dois temas: texto ≥ 4.5:1 (WCAG 1.4.3) e componentes de interface ≥ 3:1 (1.4.11). Borda de campo (`Input`, `Select`, `Checkbox`) usa `colors.borderStrong`; `colors.border` é só para divisor decorativo. Placeholder usa `colors.text.placeholder` (nunca `text.disabled`). Texto sobre um papel de cor usa o `on*` correspondente.
- Links no conteúdo são sublinhados por padrão (1.4.1); só links de navegação (logo, menus, rodapé) removem o sublinhado no próprio `.module.css`.
- Todo token de cor novo ou alterado entra na lista `contrastChecks` de `src/styles/theme/validateTheme.ts`. O teste `src/tests/styles/theme/contrast.test.ts` percorre essa lista com `contrastRatio` de `src/styles/theme/contrast.ts`, e o `validateTheme` usa a mesma lista para avisar sobre temas personalizados.
- Optional chaining (`?.`) e nullish coalescing (`??`) em vez de verificações verbosas.

## Testes

- Vitest + Testing Library + `vitest-axe` (`npm run test`). Componente novo vem com teste de comportamento por papel/nome acessível e um `axe` sem violações (use `axe` de `src/tests/axe.ts` e `renderWithProviders`).
- Testes ficam em `src/tests/`, espelhando `src` (`src/components/common/Button/index.tsx` → `src/tests/components/common/Button/index.test.tsx`). Alias `@tests/*`. Um arquivo de teste por componente; tipos próprios do teste em `types.ts` e dados em `defaultData.ts` na mesma pasta, só quando necessários.
- Infraestrutura na raiz de `src/tests/` (`setup.ts`, `axe.ts`, `renderWithProviders.tsx`, `viewport.ts`). Contratos e fixtures reutilizados por mais de um teste ficam em `src/tests/shared/` (singular): `contracts/` e `fixtures/`.
- Hidratação: `src/tests/hydration/` renderiza cada caso no servidor (Node, sem `window`, por um `globalSetup`) e hidrata no jsdom, em várias variantes de navegador (largura, tema salvo, tema do sistema; movimento reduzido num arquivo à parte, porque o `motion` guarda esse estado no módulo). As falhas conhecidas ficam em `knownFailures.ts` com `it.fails` e a causa no título. Ao corrigir uma causa, a entrada sai da lista no mesmo commit: o teste falha se um caso listado passar ou se um caso fora da lista falhar. Componente novo que lê `window`, `localStorage` ou `matchMedia` no estado inicial, ou que usa portal, entra nos casos de `cases.tsx`.
- Diálogos, modais e drawers usam `describeDialogContract(adapter)` de `@tests/shared/contracts/dialogContract.tsx` (foco, trap, Esc, `inert`, trava de scroll, axe) e mantêm no próprio arquivo só o que é específico do componente.
- `src/tests/structure.test.ts` falha se um componente com `index.tsx` não tiver teste espelho, se houver teste sem arquivo-fonte ou se uma isenção ficar obsoleta. Isenções ficam nesse arquivo, cada uma com o motivo.
- CSS Modules no Vitest viram um proxy (`css: false`): teste papéis, atributos (`data-variant`) e comportamento, não regras de CSS. O CSS do tema se testa pelas strings geradas (`themeCss`, `globalStylesCss`).
- Tudo que depende de `inert`, layout ou animação real deve ser conferido no navegador, pois o jsdom não simula esses recursos.
- Os testes de navegador ficam em `src/tests-browser/` e, no Firefox e no WebKit, rodam um arquivo depois do outro na mesma página. O `setup.ts` desmonta tudo e limpa o estado da página depois de cada teste, e estaciona o ponteiro fora da janela (`parkMouse`), porque o ponteiro que um teste deixou sobre um botão continua lá no teste seguinte e o `:hover` que sobra muda o que o `axe` consegue medir (o botão vira "incomplete", por causa do pseudo-elemento da camada de estado). O `pointerReset.spec.tsx` guarda isso. Os arquivos ficam em pastas no molde de `src/tests/`: `components/` espelha `src/tests/components` (o spec de um componente é o `index.spec.tsx` da pasta dele, e os outros têm nome descritivo, como `motion.spec.tsx`), `hooks/` guarda os hooks e o comportamento que vários componentes dividem, `styles/` os tokens, os ganchos de CSS, os estilos e as camadas, `platform/` o ambiente (servidor, RTL, toque, acessibilidade, datas, idioma e breakpoints) e `support/` os auxiliares (`harness.tsx`, `media.ts`, `pointer.ts`, `settle.ts`...); só o `setup.ts` fica na raiz, porque o `vitest.browser.config.ts` aponta para ele. Um spec que cobre vários componentes não se divide: vai para o componente dominante ou para uma das pastas transversais.

## Dependências

O build usa Vite 8 (Rolldown) e `@vitejs/plugin-react` 6. No `vite.config.ts`, `moduleSideEffects: false` vale só para o `src/` (regra por caminho), para descartar componentes que ninguém usa; as dependências respeitam o `sideEffects` de cada pacote. Um `package-lock.json` gerado com npm 11 precisa ser conferido com `npm ci` do npm 10 (o do `node:22` do Dockerfile) antes do commit.

Verifique `package.json` e o que já está importado antes de instalar algo novo — priorize o que já existe ou uma solução nativa; só instale se não houver alternativa.
